# 第 2 章 值表示

> **这一层错了不会报错，只会表现为"别的地方不对"。**
> 它是全书唯一标红的层。如果只读一章，读这章。

> **本章案例全部来自兰斯10。** 这一章里每一个症状，都是那一局里真实崩过的：
> `Invalid page index: 205644`、`this` 变成 struct #0、`m_cards` 恒 `nr=0`……
> 不是编的，日志都还在。

## 2.1 为什么它是红线

三个特征让它格外危险：

**① 症状与原因完全不像。**
栈少弹一个值，最终表现为"某个结构体的第 22 号成员是垃圾"；
容器类型标错，最终表现为"字符串索引非法"。你会在现象所在的地方修三个小时。

**② 一处错，污染一整片。**
栈偏移一格之后，**所有**后续函数调用都在错位状态下运行。
你以为在修 `A` 函数，其实 `B`、`C`、`D` 也都在错，只是恰好没崩。

**③ 单点验证不通过。**
只测一个函数看不出问题。必须在"跑完整条链"之后才暴露。

所以这一层的规矩是：**不许"先这样，回头再改"**。要么确认，要么不写。

## 2.2 三类"个数"的陷阱

字节码世界里，一个值占几个栈槽、一个函数收几个值，是三件不同的事。混淆任意两件，都会炸。

### ① 槽宽：一个"值"占几个槽

多数值是 1 槽。但**接口 / 包装类型**常占 2 槽：

```
[object 槽] [vtable 偏移]
```

关键在于**顺序**：对象在低槽还是高槽？这决定了一切下游代码。

判定方法：看它的消费方。方法调用序列长这样：

```
REF(local, 2)      ; 取第 2 个局部变量（若它占 2 槽，则结构是 [2]=obj [3]=off）
DUP2               ; 复制一份引用对
REFREF             ; 解引用一个"引用到引用"，压回 [obj, off]
POP                ; 丢掉 off
CALLMETHOD         ; 用 obj 当 this
```

`REFREF` 之后压入的第一个值是 this，那么它就是在**低槽**。

另一个判定点：返回这种值的函数，末尾必然是

```
PUSH 0
DUP_U2
SP_INC             ; 给调用方加一次引用
RETURN
```

`DUP_U2` 说明它复制了顶上的**两个**槽 —— 值占 2 槽。

### ② 参数的"个数"：逻辑参数 ≠ 槽数

函数签名里写 `nargs = 2`，但调用时压了 4 个槽，因为两个参数都是 2 槽类型。

**如果按 `nargs` 去弹参数，每次调用就少弹 2 个值。** 栈从此永久偏移。

而且它的表现形式极其阴险：函数**自己**跑得好好的（参数读对了），
但**调用方**后续的局部变量全部错位。

判定方法：遍历参数的变量表，遇到 2 槽类型就把后续那个 `void` 槽一并算进这个参数：

```c
/* 返回参数占用的槽数，不是参数个数 */
int argument_slots(fn) {
    int slots = 0, args = 0;
    while (args < fn->nr_args && slots < fn->nr_vars) {
        type = fn->vars[slots].type;
        args++; slots++;
        if (type is multi_slot)          /* iface / wrap / option */
            while (fn->vars[slots].type == VOID) slots++;
    }
    return slots;
}
```

**凡是弹参、填参、栈重排，全部改用这个函数。** 一处漏改就前功尽弃。

### ③ 返回值的槽数：由调用点的类型标签决定，不是声明

泛型返回值（"引用任意类型"）的宽度常常由**调用指令的第三立即数**决定：

```
CALLHLL lib=5 func=66 tag=12     ; tag=12 → 返回 string，1 槽
CALLHLL lib=5 func=66 tag=89     ; tag=89 → 返回接口，2 槽
```

同一个 C 函数，两次调用返回不同宽度。

最危险的写法是：

```c
if (resolved) { push(hi); push(pi); }     /* 2 槽 */
/* 未解析到元素时什么都不压，或只压 1 个 */
```

**未解析的分支必须压同样的槽数。** 空数组调一次 `Max`，就永久漏 1 槽。

## 2.3 症状 → 槽位 对照表

这是全书密度最高的一页。遇到下列症状，先怀疑对应的槽位问题。

第三列是兰斯10 里真实发生过的那一次，可以直接拿关键字去翻日志。

| 症状 | 最可能的槽位原因 | 兰斯10 实例 |
|---|---|---|
| 赋值目标变成巨大数字 / 报"页索引越界" | 栈偏移了 1 格，`dst` 取到了别的值 | `Invalid page index: 205644 (type=1)` → 委托帧短一格 |
| 对象的某个成员是垃圾，其他成员正常 | 该对象被"少填了一个槽"，后续成员整体前移 | `this` 变成堆槽 1（struct #0，3 成员），`SceneQuestMap` 读到别人身上 |
| 强转永远失败（返回 null），但对象明显存在 | 接口的 obj 被塞成了包装页而非实体页 | 40+ 次 `[nullcall] ip=0x4643C2`，`TrophyCardSet@GetList` 拿到 `this=-1` |
| 容器永远是空，`PushBack` 明明调了 | 值的槽宽判错，`offset` 被当成值传进去（=0 被当空） | `PartyCardGroup.m_cards` 显示 `nr=0`，实际是 `arr_want_elems()` 把槽数当元素数 |
| 字符串索引非法，值像指针 | 容器被标成 int 数组，元素没参与引用计数，调用方释放后成悬空 | `Invalid string index: 4693544`，泛型容器被初始化成 int 数组 |
| 一个函数返回后，**调用方**的局部变量全乱 | 返回槽宽判错（少弹或多弹） | `CALLHLL 29 3 2` 的第三立即数标 2 槽，实现按 1 槽弹 |
| 结构体副本丢失全部内容 | 深拷贝时容器成员被重新初始化成空，而非复制 | `TrophyCardSet` 6 个实例只有 5 个跑过 ctor，第 6 个成员全空 |
| 场景/对象"凭空变成另一个" | 委托传参时 iface 的两槽只拷了一个 | `Scenes::RunIScene` 把 `SceneStack` 存进了场景变量 |

> 使用建议：把这张表贴在显示器边上。它的命中率比任何调试器都高。

## 2.4 容器：三个必须同时想清楚的问题

容器（数组、列表、字典）是最容易出错的值类型，因为它有三个独立维度。

### ① 类型确立的时机

很多引擎有"泛型容器"：声明时无元素类型，由**第一次存储**决定。

```
array a;                 // 无类型
a.PushBack("x");         // 从此是 string 数组
```

如果你在初始化时**擅自默认成 int 数组**，后果是：

- 元素按 int 存（存的是槽号，看不出错）
- 不做引用计数
- 调用方 `DELETE` 之后，容器里留下**悬空槽号**
- 之后读它 → "索引非法"，而且那个数字看起来像指针

正确写法：保持"无类型"，首次存储时依据**元素的实际类型**定型，并立即参与引用计数。

### ② 所有权：谁持有引用

三条规则必须同时成立：

1. 容器插入元素时，**为自己**加一次引用
2. 调用方在传值后，**释放自己那份**
3. 容器销毁时，释放它持有的全部

少任何一条，要么提前释放（悬空），要么泄漏。

`PushBack(arr, v)` 之后 `DELETE v` 是标准序列 —— 如果容器没加引用，`DELETE` 就直接把对象销毁了。

### ③ 深拷贝还是共享

结构体赋值通常是深拷贝（值语义），但**容器成员该不该一起深拷贝**，取决于语言语义。

两种错误都很常见：

- **该共享的深拷贝了**：副本里的容器是空的新对象，写进去的东西原件看不到
- **该深拷贝的共享了**：改副本影响了原件

判定方法：看语言里容器的赋值语义。多数引擎里 `a = b`（引用赋值）是共享，
`struct.member = other` 是深拷贝，但**容器成员按共享处理**（引用语义）。

一个实用的观察点：如果副本的行为表现为"复制那一刻的状态被冻结"，那是深拷贝；
如果"后续修改互相可见"，那是共享。

### 本节三个真实失败（兰斯10）

**① `Array.Alloc` 不构造元素** → 结构体数组元素全是 0

```
m_cards = Array.Alloc(Numof(cards), -1, -1, -1)     // 只分配槽，不跑元素 ctor
```

`PartyCard` 的成员全空，界面上是 7 张带锁的卡。修法是分配后逐个 `create_struct_with_ctor`。
**判据**：`[ctor] struct=1066` 的次数 == 数组长度。

**② 槽数被当元素数** → 容器恒 `nr=0`

`PushBack` 的第二个参数在字节码里是**槽数**，实现里按**元素数**用，于是接口元素数组
（每元素 2 槽）被算成一半长度，再 ×2 一次就彻底错位：

```c
return arr_is_iface_elems(p) ? want_slots / 2 : want_slots;   // arr_want_elems()
```

**判据**：`m_cards -> array nr=N` 的 N 与 `Numof(m_card)` 一致。

**③ 谓词被忽略，过滤器恒为真** → 40 个全屏模态叠在一起

`Array.Where` 是个 stage-1 桩：`(void)predicate;` 然后把整份数组浅拷贝返回。
它不是"过滤得不干净"，而是"过滤器恒为真"，而调用方拿它当筛选器：

```
CompletedTrophy@GetNewCompleted() = g_trophyCollection.GetAll().Where(<谓词>)
```

于是"本次新完成的成就"变成"全部成就"，进部队编成时为每个成就开一个全屏模态，
40 多个叠上去把界面盖死。`[nullcall]` 从 40+ 掉到 0 只改了这一处。

> **教训**：带谓词的 HLL 桩，实现不了就返回**空数组**，别返回全集。
> 返回全集会让"过滤"静默变成"全选"，而调用方永远不会报错。

## 2.5 空值、未初始化、哨兵

三种"没有值"必须区分：

| 形态 | 含义 | 处理 |
|---|---|---|
| 空引用 `-1`（或 0） | 合法语义上的"无" | 参与比较，可赋值，需判空 |
| 未初始化 | 分配了但从没写过 | **必须**初始化为该类型的零值，不能留垃圾 |
| 哨兵（如 `-1` 表示"找不到"） | 函数返回的失败信号 | 调用方会拿它和字面量比较 |

常见事故：

- 分配器不保证清零 → 未初始化槽里是上一个对象的数据 → 表现为"新对象带着旧状态"
- 空引用没判 → 对 `-1` 取成员 → 越界
- 把哨兵当合法值存进容器 → 后续遍历时炸

一句话规矩：**每个分配点都要能回答"这个槽在第一次被读之前是谁写的"。**

## 2.6 这一层的验收标准

不通过下面三条，不许进入第 3 章：

1. **栈平衡探针归零**：每个函数 RET 时的操作数栈深度 = 入口深度 + 返回槽数（见第 5 章）
2. **容器类型正确**：泛型容器在首次存储后，`a_type` 与元素实际类型一致
3. **端到端跑一次不掉帧**：完整跑一条业务链，不出现"值类型不符"类的错误

## 2.7 一个反直觉的经验

**修这一层的 bug，"删除兜底"往往比"增加兜底"更正确。**

现象是崩溃 → 加一个判空 → 不崩了 → 三个月后发现这个判空掩盖了真正的槽位错位。

正确的顺序是：先让错误暴露（加断言而不是兜底），修好根因，再考虑是否真的需要容错。

我在项目里删掉过三处"看起来很有用"的兜底：

- 组件尺寸为 0 时用 200×30 兜底（真因是素材名解析失败）
- 空数组 `Max` 返回 `[0,0]`（真因是返回槽宽算错）
- `NULL` 目标页时跳过赋值（真因是上游传了非法引用）

三处删掉之后，各自暴露出一层更深的问题，全部修完才真正干净。
