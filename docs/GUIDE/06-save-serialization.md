# 第 6 章 存档与状态序列化

> **存档代码的错，写的时候不响，读的时候才炸；而炸的时候，写的那一刻
> 早就过去了几十分钟。** 所以这一章的判据全部指向同一个方向：
> 让"写"与"读"在没有游戏的情况下就能对账。

> **本章案例全部来自兰斯10。** 枚举全局 10449 次被写成"未设置"、
> 睡眠存档 268 次 `not implemented`、复选框状态插字段插出存档错位——
> 每一条都真实发生过，日志都在。

---

## 6.1 先分清你面对的是哪套存档

一个引擎里有**两套完全不同**的存档，混起来谈会把所有判据都用错：

| | 组存档（gsave） | 睡眠存档（resume / VM 快照） |
|---|---|---|
| HLL 入口 | `system.GroupSave/GroupLoad` | `system.ResumeSave/ResumeLoad` |
| 存什么 | 按 key+group 挑出来的全局变量 | **整个 VM**：堆 + 调用栈 + 栈 |
| 底层实现 | `savedata.c` 的 gsave 表格式 | `resume.c` 的 json/rsave 双格式 |
| 文件 | `GlobalSave.asd`、`Collection.asd`… | `00.asd` 这类自动挂起档 |
| 典型频率 | 改配置 / 进出菜单时 | 每章数次自动挂起（兰斯10 实测 268 次/批） |

**误判记录（D127）**：接存档功能时只接了 `GroupSave` 一族，
`ResumeSave/ResumeLoad` 留成空桩。此后每章 268 条
`system.ResumeSave: not implemented (…, 00.asd)` 刷了几个月日志，
直到从历史日志里按"调用期 WARNING 带次数"把它捞出来。

**判据**：接一个 HLL 库之前，先用 `--dump-hll` 把**库内序号**列全。
`system` 库的 0..9 号是 `ResumeSave / ResumeLoad / Peek / Exit / Reset /
IsDebugMode / ResumeWriteComment / ResumeReadComment / GroupSave / GroupLoad`
——Resume 一族和 Group 一族**交错排布**，按"看起来像一类"去接，
必然漏掉另一半。序号是连续的事实，类名是后贴的归纳。

---

## 6.2 序列化 switch 的 default 分支，不是错误处理，是数据销毁

gsave 的写读各有一个类型分派 switch。写端 `add_value_to_gsave()`、
读端 `gsave_to_vm_value()` 和 `json_to_vm_value()`——三处的
`default:` 都是 `WARNING` 一声然后返回 -1。

**后果**：枚举（`AIN_ENUM`，值就是整数）没有 case。于是：

- 写端：枚举全局每次存档都被写成"未设置"（-1）；
- 读端：读到"未设置"，还原成空。

**没有崩溃、没有报错面板、玩家无感知——数据就是没了。**
日志里唯一的痕迹是 `Unhandled type: enum#92`，10449 条。

**误判记录**：这条 WARNING 在日志里躺了很久没被当成事——因为它"只是
WARNING"。而它的 10449 次计数恰恰说明：每次自动存档都在丢同一批变量。
委托（`AIN_DELEGATE`，struc=-1 时名字显示成 `hll_delegate`）同型，116 条。

**判据**：

1. **序列化 switch 里每出现一种新的 `ain_data_type`，grep 三处 switch**。
   枚举、委托、long int 这些"看起来像整数"的类型最容易漏——它们不会崩，
   只会丢。
2. **"只是 WARNING"的分级要看计数**。一条 WARNING 每章 268 次 vs
   每轮 3 次，是两种完全不同性质的债。
3. 修法一律是**按整数往返**：枚举在 VM 值空间本来就是整数；
   委托写入端存的也是原始槽值。对称、无歧义、和 `AIN_INT` 同待遇。

## 6.3 顺序序列化把字段布局锁死了——三条出路各有适用场景

`save.c` 按固定顺序 `iarray_write` 一个个字段写。给 `struct parts`
**中间**插一个字段，读档端整体错位——存档格式当场作废。
但"部件上要挂点状态"的需求接二连三地来。兰斯10 移植里这个问题的
三条出路，按时间演进：

1. **旁路表（D174）**：复选框状态放 `PARTS_CB_MAX=64` 的固定容量哈希表，
   部件号回收复用时清旧记录防串味。
   适用：状态量少、生命周期跟部件走、又不想动主结构。
2. **尾挂子结构（D396）**：控件状态收进 `struct parts_widget`，
   `struct parts` 尾部只加一个**指针**。指针不参与顺序序列化，
   子结构里随便加字段。后续的音效名（槽号 2/3）、按键等待指示、
   消息窗文本区……全挂这里，一个字段吃下整个控件家族。
   适用：一族相关状态、需要统一生命周期（部件释放时一并 free）。
3. **尾部追加标量（pixel_decide / enable_input_process）**：单个 bool
   加在结构体**最末尾**（指针字段之后），同样不参与顺序序列化。
   适用：单个标量、要被每帧输入循环高频读（过一层指针不划算）。

**判据**：先问"这个状态要不要持久化"。**不需要**的（菜单重建时
AIN 会重设的 UI 状态、生命周期跟部件走的运行期标记）才有资格走
尾部/旁路——需要持久化的状态本来就在顺序区里，别乱动它。

## 6.4 "写不进"和"该写"是两回事——先查声明，再定性

日志里 563 条一组的告警：

```
save: array with unsettled element kind (a_type=79, N elements)
      written as unset at ReplayMemo.m_eventName (root g_replayMemo)
```

三个根（`g_replayMemo` / `g_newMark` / `g_assistantCollection`）每轮
自动存档都报。乍看像"回想/收藏数据在丢失"。**离线查证两步**：

1. `--dump-structs`（成员类型列）：三个成员在 AIN 里声明的就是
   **类型码 79 = `array<?>`**——泛型、声明侧就没有元素种类；
2. 泛型数组的元素种类靠**第一次写入**定型（`a_type` 从 79 变具体类型）。
   这三个数组在存档时刻还没被写过——没有数据可丢。

**结论：良性噪音。** 它和 6.2 的枚举丢失是同一条 WARNING 通道里的
两种相反情况——区别只在于**声明侧有没有元素种类**。

**判据**：

- 序列化告警的定性顺序：**先查声明（`--dump-structs` 的类型码），
  再查运行期（这个数组被写过没有）**，然后才谈修复；
- 声明是泛型 + 未写入 ⇒ 写"未设置"是**正确行为**，告警可以限流；
- 声明是具体类型 + 有数据 ⇒ default 分支丢数据，是**真 bug**（6.2）；
- 反过来，"从声明侧补元素种类"这条路是**错的**：泛型的定义就是
  声明不知道，硬猜会把"诚实的不确定"变成"自信的错误"。

## 6.5 睡眠存档的外壳很薄——但语义是"整个世界"

`system.ResumeSave(key, file, ref int n)` 的实现只有三行：
调 `vm_save_image(key, file)`，把返回值写进出参，返回非零。
**但它的语义是把堆、调用栈、栈整个序列化**——`00.asd` 里躺着的
是"此刻的整个世界"。

两条纪律：

1. **ResumeLoad 之后不要再信当前 C 栈帧**：它会把调用栈整个换掉。
   上游把它做成 syscall，游戏只在"从上次挂起继续"那条路上用——
   那时当前帧本来就该被丢弃。任何"load 完再干点活"的代码都要过一遍：
   你引用的指针还活着吗？
2. **ref int 出参收返回值、bool 返回成功**——这个形状来自上游
   `SYS_RESUME_SAVE` 的 syscall 签名，不是猜的。配对函数的形状
   要互相印证（`ResumeLoad` 是 void，因为没有"成功值"可回传）。

## 6.6 序列化的缺口清单，从两个静态来源交叉

第 3 章 3.53 讲了"日志 WARNING 是语义缺口清单"。落到存档域，
还有第二个来源——**声明表**。两者交叉：

| 来源 | 能回答 | 不能回答 |
|---|---|---|
| 调用期 WARNING（带次数） | 哪条路径真的丢过数据、丢了多少次 | 哪些类型**将来**会丢 |
| `--dump-hll` / `--dump-structs` 类型码 | AIN 声明里有多少种类型要过 switch | 运行期真的走到没有 |

交叉的用法：把 `ain_data_type` 全集列出来，对序列化 switch 逐个
比对——**离线就能证明"哪些类型还没有 case"**，不需要等运行期踩到。
`AIN_ENUM` 的 10449 条 WARNING 本质上是可以提前算出来的：
类型集里有枚举，switch 里没有枚举，仅此而已。

**判据**：每加一种值类型、每扩一处序列化 switch，
**全集比对表**要跟着更新。它比"想起来再查"可靠，
比"跑测撞上"便宜两个数量级。

## 6.7 这一层的验收标准

- [ ] `--dump-hll` 列全库内序号，没有"按类名接、漏掉交错成员"；
- [ ] 写/读两侧（加上第三处：外部格式校验器）的类型分派 switch
      与 `ain_data_type` 全集对过账，没有"看起来像整数"的类型落在
      default；
- [ ] 每条"写为未设置"的路径，读侧都有对应的还原分支（写 -1、
      读侧却要求 `0 <= v < n` 是自断回路，见 5.8）；
- [ ] 不持久化的状态全部挂在顺序序列化区之外（6.3 的三条出路之一），
      并注明为什么不持久化；
- [ ] "良性噪音"有查证记录（声明 + 运行期两步），没有被静默降级；
- [ ] 睡眠存档的 load 路径之后，没有任何代码引用 load 前的 C 栈对象。
