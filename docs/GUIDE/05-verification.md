# 第 5 章 端到端验证

> 前四层是"怎么修"，这一章是"怎么知道自己修对了"。
> 没有这一章，前四章会退化成"改到不崩为止"。

## 5.1 三个判据

一个移植是否健康，看三个指标。它们互相独立，缺一不可。

| 判据 | 回答的问题 | 灵敏度 |
|---|---|---|
| **栈平衡** | 值表示对不对 | 极高，能抓到 1 个槽的偏差 |
| **差分对照** | 这次改动到底改变了什么 | 高，能排除"碰巧好了" |
| **出画** | 端到端是否真的通了 | 粗，但不可伪造 |

前两个在日志层，第三个在像素层。三个都过，才算过。

## 5.2 栈平衡探针

这是全书**投入产出比最高**的一个工具，二十行代码。

### 原理

字节码函数的操作数栈收支是确定的：

```
RET 时的栈深 == 进入函数、弹完参数后的栈深 + 返回槽数
```

不等就说明有一方算错了槽数。

### 实现

```c
/* 1) 记录基线：在弹完参数之后（不是进入函数时） */
int nslots = argument_slots(fn);
for (int i = nslots - 1; i >= 0; i--)
    locals[i] = stack_pop();
frame->entry_sp = stack_ptr;          /* ← 关键：此时参数已经不在栈上 */

/* 2) RET 时比对 */
int want = frame->entry_sp + return_slots(fn);
if (stack_ptr != want)
    WARN("fno=%d %s want=%d got=%d", fno, name, want, stack_ptr);
```

### 三个必须踩对的细节

**① 基线要取在弹完参数之后。**
在函数入口取基线，会把参数算进去，导致每个函数都"不平衡"。

**② 方法调用要额外修正。**
`CALLMETHOD` 的 `this` 和 `fno` 是在 `function_call()` **之后**才弹的：

```c
function_call(fno, ret);      /* 弹参数，这里记的基线偏高 */
stack_pop();                  /* fno */
stack_pop();                  /* this */
frame->entry_sp = stack_ptr;  /* ← 重新记一次 */
```

不修正这一处，所有方法调用都会误报差 2。

**③ 通过非标准路径进入的帧要标记跳过。**
委托调用、HLL 回调构造的帧没有基线，用 `entry_sp = -1` 标记并跳过。

### 用法

第一次跑就应该有输出。它会直接点名"哪几个函数不平衡、差几个槽"。

剩下的工作变成：对着这份名单，逐个查它的参数/返回值槽数。

> 我一开始拿到 12 个不平衡点，全是"差 2"，全指向同一个原因：接口类型按 1 槽弹了。
> 修一处，名单归零。

## 5.3 差分对照

改完一处后，怎么确认是"这处改动"起了作用，而不是别的？

**做法：单变量，跑两次，只比一个指标。**

```sh
# A：新代码
XSYS4_HLL_ARGDBG=1 tools/xsys4 run a 70

# B：把改动临时关掉（if (0 && ...)）
XSYS4_HLL_ARGDBG=1 tools/xsys4 run b 70

diff <(key_lines logs/a.log) <(key_lines logs/b.log)
```

注意"只比一个指标"：`argdbg` 从 60 条降到 0 条，就是一个干净的结论。
如果同时看五个指标，你会陷入"好像都变好了一点"的模糊判断。

差分特别适合这几种场合：

- 确认某个探针的输出确实来自你想的那条路径
- 确认"修好了"不是"崩得更早所以看不到了"
- 二分：把嫌疑范围从 10 个函数缩到 1 个

### 指标一条不变，等于改动没打到路径

差分最容易自欺的地方，是"我改了，所以应该有效"。判据只有一个：
**主指标必须变**。兰斯10 移植里曾有单局上万条 `double free` 告警；
从代码看，函数参数写进局部页时只给 `ref` 类型加引用，而页销毁时释放
所有引用成员，不对称得刺眼。补上引用、重新编译、跑同一条序列——
告警数 **13720 → 13720**，连热点指令的地址分布都逐条相同。

这个"一模一样"比"变差了"更有信息量：它说明改动根本不在那条执行路径上，
而不是修错了方向。此时正确动作是**立即回退**，把这次证伪写进债务台账，
再换一层取证；把看起来合理的 diff 留在工作树里，下一轮就会有人
在它上面继续堆假设。

配套纪律：

- 修复自带一个默认开启、可用环境变量关掉的 A/B 开关，别靠改代码再编译做对照
- 对照用同一序列、同一超时、同一截图点；随机点击的抖动也要记下来
- 至少盯一个**计数型**主指标（告警条数 / ERROR 数 / 装载数），
  再加一两个"别被修坏"的护栏指标
- 台账里同时写"证伪了什么"，它和"修好了什么"一样值钱
- **对照必须跑全默认配置**。取证期随手设的诊断开关会一路继承到子进程，
  两组跑的就不是同一个程序。基线脚本第一件事应该是清掉所有诊断变量，
  只给受控 A/B 留一个显式白名单
- **先验证那把尺子**。某次基线脚本把计数写成 `grep -ac ... || echo 0`：
  `grep -c` 无匹配时会**输出 `0` 但返回 1**，于是又补一个 `0`，指标里
  凭空多一行。差分类实验的全部前提是测量工具自己不撒谎；上线前用
  "已知为 0"和"已知为 N"两组输入各验一遍
- **能用离线静态检查证伪的假设，别用跑测去试**。怀疑"建框架用 A 个槽、
  拆框架用 B 个槽"，写一个 30 行小程序读元数据把两者对全量数据比一遍，
  几秒就能得到"1276 项全部相等"。跑一轮端到端要几分钟，而且指标不变
  时你分不清是"假设错了"还是"没打到路径"
- **全局兜底比定位到具体点更危险**。栈被污染时，"给所有这类帧强制恢复
  栈顶"看起来很稳妥，实测却让程序连启动画面都进不去。宁可多花一轮
  把"哪一次调用、哪个回调"打出来，也不要引入一个作用于整类路径的
  隐式修正

## 5.4 出画判据

不要用"我看了一眼好像有画面"。用可量化的：

```sh
magick shot.png -colorspace Gray -format "%[fx:mean]" info:
```

| 值 | 含义 |
|---|---|
| `mean ≈ 0` 且文件 < 1 KB | 纯黑，什么都没画 |
| 文件 < 1 KB | 大概率纯色 |
| 文件 > 1 MB 且 `mean` 在 0.1~0.6 | 有真实内容 |

再配一张人眼可看的缩略图，确认"有内容"和"内容对"是两件事。

**自动化的价值**：`file_size == 390` 这个常数比任何描述都可靠 ——
它意味着"这一帧和上次完全一样"。连续三次都是 390，就是画面冻住了。

## 5.5 探针的工程化

探针会失控。三条规矩：

**① 环境变量控制，默认关闭。**

```c
if (getenv("XSYS4_SP_BALANCE")) { ... }
```

绝不能默认开启 —— 它会拖慢十倍，而且日志淹没一切。

**② 带上限 —— 但上限要按"去重键"，不是按"条数"。**

```c
static int n;
if (n++ < 40) NOTICE(...);      /* 前 40 条足够看出模式 */
```

日志无上限 = 跑一次几 GB = 磁盘爆掉 = 手机存储炸过。

但**同一批对象每帧重画时，按条数限流会被最先出现的那几个吃满**，
后面的部件一条都打不出来 —— 于是"没输出"被误读成"没发生"。
任务地图上排查選択肢按钮时，`[flat]` 探针的 40 条全被打在同一个
背景部件上，真正要看的按钮一次都没轮到。

按对象号去重，每个号只打一次：

```c
static int seen[32], nr_seen;
bool dup = false;
for (int i = 0; i < nr_seen; i++)
    if (seen[i] == parts->no) dup = true;
if (!dup && nr_seen < 32) { seen[nr_seen++] = parts->no; NOTICE(...); }
```

**③ 探针要打"设置动作"，不要只打"结果快照"。**

快照可能拍在设置之前。真实案例：`[parts]` dump 里按钮 `pos=(0,0)`、
父 `par=-1`，一度据此判断"`SetPos` 没生效、挂父失败"；实际
`SetPos(307, 1438, 362)` 和 `SetParent(325 → 323)` 都发生在 dump 之后。
改成在 `PE_SetPos` / `PE_SetZ` / `PE_SetParentPartsNumber` 入口打
「谁、设成什么」，一次就定位，而且顺带看出一件事：
**按钮的 `z` 是 100、面板的是 22000 —— 前者本该是相对父的偏移**。

**④ 全局 dump 的 tag 不是归属。**

`PE_DebugDumpParts(tag)` 的 `tag` 只是"谁触发这次 dump"，
被打印的是**整张**部件列表。按 tag 去 grep，会把别的活动的旧部件
当成本次新建的 —— 我因此把 `900000230/231/232`（另一活动的
`Base`/`Flat` 角标）当成選択肢按钮，得出"按钮全是 0x0、没有几何"
的错误结论，白花了一轮。判断归属要看 `parts_no` 的分配时序
（后装载的活动号更大），或者直接看建造日志的先后。

**⑤ 用完即删，或者"升级为常驻诊断"。**

判断标准：

- 只在本次调查有用 → 删
- 以后再遇到同类问题还能用 → 保留，写进文档的"诊断开关表"

我在项目里保留了 7 个常驻诊断（调用追踪、栈平衡、逐指令栈深、HLL 收支、
部件构建、赋值现场、函数实参转储），删掉了 20 多个一次性探针。

**留下的标准不是"有用"，而是"下次还会用"。**

## 5.6 可证伪假设

排查时最大的浪费不是"猜错了"，而是"猜错了却不知道"。

每个假设都要写成**可以被一次实验否掉**的形式：

| 坏假设 | 好假设 |
|---|---|
| "可能是渲染有问题" | "如果渲染没被调用，那 `scene_render` 的调用计数在本场景期间应为 0" |
| "可能是数据没加载" | "如果数据没加载，`parts_set_flat` 应返回 false；日志里它返回 true，所以不是" |
| "可能是槽位错了" | "如果槽位错了，栈平衡探针应在本函数上差 1；实际差 0，所以不是" |

**假设被否掉是好事**，它排除了一整片区域。真正的危险是那种"怎么都说得通"的假设。

## 5.7 从"能跑"到"跑对"

不崩、不报错、有画面 —— 这三条达成后，还剩最难的一段：**行为对不对**。

方法是"对比锚点"：

- **已知正确的旧版本**：同一份数据在新旧实现上跑，比较输出
- **游戏自身的校验**：很多引擎会校验数据一致性，让它替你判断
- **可数的量**：帧数、对象数、字符串长度 —— 这些能对数，不用眼睛看

最后一句提醒：

> **"零错误"不是通过标准。**
> 我见过多次"零错误 + 全黑"的状态 —— 恰好说明了这一层的重要性。
> 通过标准是"三个判据同时成立"，而不是"日志干净"。

## 5.8 写出去的东西，要能被自己读回来

序列化是最容易"静默错"的一段代码：写的时候不崩，读的时候才炸，而炸的时候
已经不记得当初写了什么。一个真实的结构：

- 泛型容器在**声明**里没有元素种类（那正是"泛型"的含义），秩也可能只是
  占位符。写档时若照声明取值，会把元素写成"未知类型"；
- 读档时按存档反推元素种类去分配，再逐元素比对类型 —— 于是写出去的文件
  必然对不上，报"元素类型不符"；
- 更隐蔽的一层：解析器校验函数只认具体容器类型，泛型落在 `default` 分支
  直接 `return false`，**整份文件被判为无效**。文件是完整的 zlib 流，
  校验和也对，只是没人接受它。

判据只有一条，而且必须自动化：

> **写出去的文件，用同一个解析器读回来，必须成功，且关键结构可数。**

三个实践要点：

1. **写一个离线检查器**，不跑游戏、秒级返回：解析每个存档，打印
   "OK / Invalid"、每张表的条目数、每个容器的秩与元素类型、以及全局变量
   指向的索引是否越界。它比任何跑测都便宜，比任何肉眼都快。
2. **"记不下"要显式**。元素种类未知、结构体槽指向的不是结构体页 —— 这些
   情况下正确做法是写成"未设置"（一个约定的哨兵值），而不是把垃圾值当
   数据写出去。前提是这个哨兵在读侧也被接受：写 `-1`、读侧却要求
   `0 <= v < n`，等于自断回路。
3. **表索引一律当作不可信输入**。索引来自文件，可以是 `-1`（未设置）、
   可以越界（旧版本写的、截断的）。先在边界检查，再解引用；`-1` 统一
   解释成"没有值"，因为调用方对"空"本来就有处理路径。

顺带一条环境纪律：**测试夹具也算被测对象**。某轮跑测"存档修好了"的结论
反复不成立，最后发现跑测脚本的清档命令 `rm -rf` 被沙箱包装后**静默失败**，
每轮读的都是两个月前的旧档。夹具不干净时，A/B 的差异信号会被旧数据淹没。
把夹具变成显式输入（一个目录参数），并在结果里打印"这次用了哪个目录、
产生了几个文件"，是成本最低的防呆。

## 5.9 值不对，先问"是不是同一个对象"

有一条误判我付出了三轮跑测才纠正，值得单独写下来。

现象：某个双槽值（接口值 `[对象, 偏移]`）在读取点第二槽是个巨大的数，
看起来像"被覆盖成堆槽号"。我按直觉在**写入端**找凶手：

- 追加元素的函数写入 `[obj, 0]`，写入瞬间回读也是对的；
- 在页变量写入的统一入口下断点，零命中；
- 想起还有"通过指针直写"的路径，补了第二个断点，仍然零命中。

三个"零命中"其实已经指向答案，但我当时读成了"还有没找到的直写点"。
真正该问的是：**我看到的那份数据，是不是当初写的那一份？**

后来在写入和读取两侧各加一行页指针打印，一次性定案：

```
写入侧  p=0x...787bae20   -> [obj, 0]
读取侧  ptr=0x...7b4abb40 -> [obj, obj+16]
```

两个指针不同 —— 中间有一次**复制**。语言里"取容器引用"的那条指令
在本引擎里实现成了"深拷贝整个页"，而复制循环对每个槽都用同一个元素类型
去做 `copy(value, type)`。双槽值的第二半是**小整数元数据**，不是引用；
被当成引用复制，就会被当成"堆槽 0"再制造出一个全新的对象槽。
于是值在复制的那一刻就坏了，后面所有在写入端找覆盖者的努力都是白费。

可复用的判据：

1. **先打两侧的对象身份（指针/句柄），再谈值怎么坏的。** 身份不同时，
   值不同的解释是"复制语义错"，不是"谁改了内存"。
2. **把"零命中"当成强信号。** 覆盖了所有已知写入路径仍然零命中，
   几乎等价于"根本没有发生过写入"。
3. **复合值的每个槽不一定同一语义。** 只要某个槽是"元数据"（偏移、
   标记、长度），凡是按统一元素类型遍历容器的代码（复制、序列化、
   初始化、释放）都要单独处理它。这次是复制，上一章的存档是序列化，
   同一个坑换了件衣服。
4. 修完仍要用"关掉修复能否复现原错"收尾；否则你只是把一个现象
   挪到了别处。

## 5.10 帧被弹歪了，先数槽

有一条症状特别有欺骗性：**在正确对象上调用的方法，进入函数体后 `this` 变成了另一个对象**。

现场是这样的：某个属性的写入口读自己的成员，一切正常；紧接着它调自己的
"写入后回调"，回调第一句读第 4 个成员，就报越界——越界的页只有 3 个成员，
和被调函数所属的类**完全不是一个类型**。

这里最容易走偏的两条路：

- 怀疑"对象被释放、堆槽被回收复用"（这个引擎确实有槽号回收，很像）；
- 怀疑"回调注册时绑错了 `this`"。

两条都错。真正要问的是：**这次调用到底弹了几个槽？**

判据只需要一行日志。在 CALLMETHOD 的派发点，把三样东西一起打出来：

```
调用点现场：  nargs=2  obj=133495 (struct 660, 5 成员)   ← 完全正确
进入函数后：  nargs=2  slots=3   sp=38->33              ← 多弹了一个
```

`nargs` 是字节码里写死的**逻辑参数个数**，`slots` 是按被调函数声明算出来的
**物理槽数**。两者一旦不等，`[obj, fno]` 就会被当成参数弹掉，
`this` 便落到栈上的残留值上——本例是 `1`，恰好是引擎里一个 3 成员的内置对象，
于是越界位置和"对象类型不对"全都对得上。

再往下一层，为什么物理槽会多算？这个语言的属性写入口（`postset`）声明长这样：

```
vars = [WRAP oldValue, VOID, <编译器临时>, <编译器临时>]
nr_args = 2
```

`WRAP` 是双槽值，第二槽以 `VOID` 占位。槽数计算函数看到 `WRAP` 就去跳过
后续的 `VOID`，**但忘了让参数计数也加一**；循环于是认为"还有第二个参数没算"，
把紧随其后的**编译器临时变量**（名字里通常带 `dummy`）当参数吃了进去。

可复用的判据：

1. **`nargs != slots` 就是错，别解释。** 两个数来自不同信息源（字节码立即数
   和函数声明），任何不一致都意味着调用约定被违反。把它做成默认开的断言日志。
2. **槽数计算里"跳过占位槽"和"参数计数"必须同步走。** 凡是 `i++` 跳过声明槽
   的地方，都要问一句"这算不算一个逻辑参数"。
3. **别用"参数个数"当"槽数"的同义词。** 双槽值（接口、包装、可选值）让两者
   分家；一个函数可以 `nr_args=2` 而只压 2 槽，也可以 `nr_args=1` 而压 2 槽，
   取决于声明形式。以声明为准去算，以立即数为准去弹。
4. **帧错位的症状永远是"别人的成员"**，不是"读不到值"。看到"这个对象怎么只有
   N 个成员"时，先怀疑栈，再怀疑对象。

配套的取证工具（不需要调试器）：一个"在指定指令停一次并转储当前帧"的开关。
转储要包含三样东西才够用：

- 当前帧的**全部局部变量**（名字 + 声明类型 + 值 + 引用页的形状）；
- **`this` 页本身**以及它前十几个成员，成员是容器时再把容器的前几个元素打出来；
- **字符串的值本身**（不是堆槽号）。

最后一条是血泪：一次下标算错，局部变量里 `index = -1`，但从堆槽号上完全看不出
为什么是 -1；把字符串内容打出来才发现传进来的是 `"Tab1"`，而切片函数取到的是
第二个字符——切片差一位，下标就成了 `-1`，随后 `array[-1]` 是空引用，
方法号解析成 `-1`。**"容器空"和"下标错"是两种病**，转储里必须能分开。
