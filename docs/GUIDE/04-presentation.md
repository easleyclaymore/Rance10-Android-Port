# 第 4 章 呈现与输入

> 前两层让游戏"算得对"，这一层让它"看得见、点得着"。
> 这一层的错误通常不报错，只是**什么都不显示**。

## 4.1 编号体系以游戏为准

凡是"编号 → 含义"的映射，一律以**游戏自己的代码**为准，不看开源实现。

| 编号体系 | 出处 | 常见分歧 |
|---|---|---|
| 组件类型 | 引擎的"类型名"函数 | 开源实现是旧版编号，整体错位 |
| 事件码 | 事件分发表 | 新增了几种事件，序号后移 |
| 部件状态 | 状态名表 | 状态数量随版本增加 |
| 资源类型 | 加载器分派 | 新增格式插在中间 |

症状统一是"**东西建出来了，但按错误的类型处理**"：

- 按钮被当作 `SpinBox` → 尺寸为 0 → 命中测试永远失败 → "点击没反应"
- 文本被当作 `CG` → 找一个不存在的图片 → 显示空白

**判定方法**：把构建日志里的"实际类型"和"类型名表"对齐，一行一行核。

## 4.2 资源格式的版本分叉

同一个扩展名，不同版本的结构可能完全不同，而**加载器往往只实现了其中一个版本**。

真实案例（flat 格式）：

| 版本 | 图形键结构 |
|---|---|
| v < 15 | `count` + `keys[frame]`（每帧一个键） |
| v ≥ 15 | `frames[frame].keys[i]`（每帧**每个图层**一个键） |

加载器两个都解析了，但渲染器只写了 v<15 的路径：

```c
if (local >= tl->graphic.count) continue;   /* v15 的 count 恒为 0 */
```

结果：所有 timeline 被跳过，**每一个界面都不画**，但没有任何报错、没有任何"未实现"。
加载成功、尺寸正确、`show=1`、`alpha=255` —— 一切看起来都对，就是不显示。

**这一类问题的排查方法**：

1. 确认"数据在不在"（打印解析后的结构体字段，不要只打印"加载成功"）
2. 确认"渲染路径走没走"（在绘制函数入口打点，看是 0 次还是 N 次）
3. 两者都对，才是"画了但看不见"（坐标 / alpha / z 序 / 视口）

这三步能把"不显示"从玄学变成二分。

> 教训：`count == 0` 这种"合法的空值"是最难查的，因为它不越界、不报错。
> 凡是"遍历集合"的地方，都要能回答"这个集合为什么是空的"。

## 4.3 谁驱动渲染：这是架构问题，不是 bug

"画面不更新"最常见的原因不是画错了，而是**根本没人让它画**。

三种常见架构：

| 架构 | 谁决定重绘 | 典型症状 |
|---|---|---|
| 脏标记驱动 | 状态变更时置 dirty，主循环见到才画 | 某类变更忘了置位 → 卡在旧帧 |
| 每帧无条件重绘 | 主循环固定画 | 简单可靠，代价是 CPU |
| 事件驱动 | 窗口 expose / resize 才画 | 窗口被遮挡后不恢复 |

如果你按"脏标记"实现，就必须保证**每一类状态变更都会置位**：

- 部件增删
- 部件属性变化（位置、透明度、显示与否）
- 动画帧推进
- **场景压栈 / 弹栈**（最容易被忘的一类）

漏掉任何一类，都会得到"某个界面就是不显示，其他都正常"。

判定方法：在渲染入口统计"每帧是否被调用"。如果某个场景期间一次都没调用，
问题在驱动方，不在渲染方。

> 我在项目里踩过：渲染被 `scene_is_dirty` 门控，而置位它的只有 `scene_set_wp()` 这类少数调用点。
> 没有任何 AIN 代码会为"一个静态对话框压栈"置位，于是窗口永远停在最后一次 3D 画面。
> 改成每帧提交后，这条线才通。

## 4.4 坐标与命中测试

命中测试失败通常有三个来源，按概率排序：

1. **尺寸为 0**（素材没加载成功，但部件建出来了）
2. **坐标系不一致**（部件坐标是"相对父容器"还是"绝对"，缩放前还是缩放后）
3. **层级顺序错**（被上层透明部件挡住了）

坐标换算的坑：

- 引擎按固定分辨率渲染（如 1920×1080），窗口可能是任意尺寸
- 鼠标坐标是**窗口坐标**，命中测试用的是**渲染坐标**
- 两者之间的换算由画面缩放/黑边决定

验证方法：先假设"命中测试是对的，只是坐标错了"，直接点部件的**中心计算值**。
如果点中了，说明是坐标问题；点不中，再查尺寸和层级。

要拿到部件坐标，最省事的办法是让构建日志把 `name / pos / z / size / show` 全打出来 ——
这一次性投入会在后续每次调试里回本。

## 4.5 输入时序

"点了没反应"有时是时序问题：

- 场景刚压栈，事件处理器还没注册完 → 前 1~2 帧的点击被丢弃
- 淡入动画期间输入被屏蔽（这是设计，不是 bug）
- 事件在**下一帧**才派发，而测试脚本点完就截图

自动化测试里要留足等待：等"目标界面已加载"的标志出现，再点击，再等 2~3 帧才截图。

### 4.5.1 场景退出要两个条件同时成立

把 `SceneStack`（函数号 29645–29668）整个读一遍，字段其实很少：

| 成员 | 是什么 |
|---|---|
| `m6` = `LayerPartsNumber` | 本场景的图层号；`AddLayer()` 里等于 `AFL_Parts_AddLayer(-1)` |
| `m7` = `IsFinish` | `Exit()` 唯一做的事就是把它置真 |
| `m1` / `m2` | `WaitFrame()` 的帧计数与「等待结束」就绪位 |
| `IsShow` | **不是字段**：`AFL_Parts_IsLayerShow(m6)` 的返回值 |
| `IsActive` | **不是字段**：`AFL_Parts_GetActiveLayer() == m6` |

`Join()` 的循环是 `while (!m7) WaitForClick(0)`，所以「场景结束」需要两件事都发生：

1. `Exit()` 把 `m7` 置真（本作走的是 `Overlay@FadeOut(1500, dg(SceneStack@Exit))` 这条回调）
2. 一次能被 `WaitForClick` 消费的点击 —— 它唯一的 break 是 `GetClickNumber() > 0`

**只做到第 1 件，场景不会退出。** 画面会停在淡出后的状态，`[act] loaded` 不再增长，
看起来像「点按钮没反应」，实际是循环还在等一次点击来喂饱 `Join`。

`WaitFrame()` 同样不是「等一帧」：它新建图层 → 把 `m1`/`m2` 清零 →
把 `CheckWaitExit` 挂成 `AFL_Parts_AddBeginUpdateEvent` 的每帧回调 → 隐藏图层 →
自旋到 `m2` 变 1（`CheckWaitExit` 的条件是 `m1 > 3`，即连续 4 帧，或回调参数 `< 17`）→
撤回调、显示图层、删图层。它是**节流 4 帧**，不是同步一帧；
跑测里「画面几十毫秒才动一下」多半就是它。

### 4.5.2 一个场景只有一个阻塞点

把 `SceneTurnStart@Run` 的调用序列整条列出来：

```
Music.Play(…)
Overlay.FadeIn(…, dg)      ; 只注册淡入完成回调
LPYearView.FadeIn()
instantTimer(dg1)          ; 延时后调 TurnNumberViewGroup.Slide
instantTimer(dg2)          ; 延时后调 LPYearView.Slide
SceneStack@Join()          ; ← 唯一的阻塞点
```

旁边那些 `FadeIn` / `Slide` 都不阻塞：`Overlay@FadeIn` 里只有一个
`DG_CALLBEGIN 1077 / DG_CALL 1077, END` 的 foreach，调的是**传进去的回调**；
真正推进它们的是 `View_Update` 的动画时钟。

所以「界面卡住」永远只有一个位置可查 —— `Join` 里那个 `WaitForClick`。
它不等帧、不等动画、不等资源，只等两件事：`GetClickNumber() > 0`，
以及外层 `while (!IsFinish)` 的 `IsFinish`。

`parts::detail::WaitForClick`(7659) 和 `parts::WaitForClick`(7221) 全项目
只有 2 个 AIN 调用点，`WaitForClick` 内部也只有 2 个真正的实现入口
（8309 的直接调用者只有 7221 与 7659）。**不存在「另一个等待把点击抢走」的可能**，
排查时不必去怀疑并发等待。

### 4.5.3 `WaitForClick` 的三个出口，`Exit` 会打通第二个

循环只有三个出口：

1. `0 < GetClickNumber()` —— 点击。`clicked_parts` 由「按下沿 + `click_eligible`」
   的 `click_down_parts` 在释放沿转写
2. `global2 != 0` —— 由 `parts::detail::EndWaitForClick`(8310) 置位
3. `local1` 分支里的 `CASClick`（`Join` 调用时 `local1 = 0`，整段跳过）

**`SceneStack@Exit` 的完整实现只有三句**：

```
m7 = true                              ; IsFinish = true
AFL_Parts_EndWaitForClick(0)           ; → global2 = 1
return
```

所以 `Exit` 是「置位 + 打断等待」一体的，理论上 `WaitForClick` 下一次循环检查
就会从第 2 个出口退出，**不需要玩家再点一次**。

**上一版这里写错了**：我只读了 `Exit` 的前 56 字节，看到 `m7 = true` 就收工，
漏掉了后面那句 `EndWaitForClick`，于是得出「场景结束还要再点一次」的错误结论。
判据很直接 —— `EndWaitForClick`(7112) 的调用者列表里就有 `SceneStack@Exit`(29658)。
读函数要读到 `RETURN`，不能读到「看起来做完的那一句」。

### 4.5.4 `Overlay@Fade` 有两条路，`dg` 可能比 `Join` 还早

`Overlay@FadeOut(from, to, dg)` 只是转调 `Overlay@Fade`(22643)，后者是：

```
SetShow(1)
if (GetAlpha() == 0) {        ; 已经全透明
    SetShow(0)
    foreach (f in dg) f()     ; ← dg 当场执行
    return
}
Parts@Motion(…)               ; 否则启动补间，dg 在动画完成时由 CASTask 调
```

所以 `FadeOut(1500, dg(SceneStack@Exit))` 里的「1500ms」只在 overlay 当前**不透明**时成立；
如果它已经是 `alpha = 0`，`Exit` 会立刻执行。

这条语义反转了一个很自然的假设：**`Exit` 未必发生在 `Join` 之后，它可能更早。**
如果 `Exit` 先跑完，`m7 = true` 和 `global2 = 1` 都在等待开始前就设好了，
`WaitForClick` 第一轮就会从出口 2 退出 —— 那才是正常路径。

反过来说，实测里「`Exit` 触发了但 `Join` 不返回」就不能再往这条链上找原因：
`Exit` 已经把两个出口都打开了，剩下的只可能是 `Join` 读的 `m7` 和 `Exit` 写的
`m7` 不是同一个实例字段。这一层静态分析到此为止。

### 4.5.5 `SceneTurnStart` 的生命周期

| 方法 | 动作 |
|---|---|
| `@0(stack)` | `m1 = stack`（构造参数，不是自己 new）；`local1 = GameContext.Turn` |
| `@Run` | `FadeIn` → `LPYearView.FadeIn` → `instantTimer×2` → **`m1.Join()`** |
| `@OnFinishFadeIn` | `FadeInButton(dg = OnFadeInButtonFinishEvent)` |
| `@FadeInButton` | 建三个按钮、各挂委托、启动出现动画（844 字节，D397 改的就是它） |
| `@OnFadeInButtonFinishEvent` | `ThumbnailCapture.Capture()` + `LocalSave.AutoSave(0)` |
| 玩家点按钮 → `@FadeOut` | 全屏黑遮罩 + `Overlay.FadeOut(1500, dg = SceneStack@Exit)` |
| `SceneStack@Exit` | `m7 = true` + `EndWaitForClick(0)` |

**`m1` 是构造时传进来的那个 `SceneStack`**，`Run` 的 `Join` 与 `FadeOut` 的 `dg`
都绑在它身上 —— 同一个实例，不存在「两个 stack」的错位。

顺带记一条实用事实：跑测里的 `logs/savedir/<tag>/LocalSave5000.asd` 就是这个
`OnFadeInButtonFinishEvent` 写的 `AutoSave(0)`。它不是定时器产物，
而是**按钮出现动画播完那一刻** —— 所以有这个文件，就等于「回合开始屏已经完整显示过一次」。

### 4.5.6 三个按钮的入场：三段补间 + 一个完成回调

`@FadeInButton(dg)` 那 844 字节其实是一种句式重复三遍：

```
task = btn.Motion()                ; TextButton@Motion() 取该按钮的补间任务
task.SetPos(-300.0, 0, 0, 0, 1)    ; x 从 -300 滑到 0
task.SetAlpha(0.0, 1.0, 0)         ; 同时淡入
```

三个按钮（`m4` / `m3` / `m2`）各一遍，然后
`PartsMotionTask@SetOnFinishEvent(dg)`(29719) 把完成回调挂到其中一个任务上。
全函数只出现一次 `SetOnFinishEvent`，所以 `@OnFadeInButtonFinishEvent`
（截图 + 自动存档）整体只触发一次。

`SetPos` 五个参数里第一个是 `0xc3960000`，也就是 **-300.0**，后三个 `0.0`、最后一个 `1`；
`SetAlpha` 三参数是 `(0.0, 1.0, 0)`。这就是「从屏幕左侧滑入并淡入」。

挂回调的那个任务（`local9`）的构造在 `0x36c1a4` 的 `REFREF + PUSH 5 + ADD` 里，
目前只读到「从某个结构引用偏移 5 取出来」这一层，没有再往下拆 —— 但
「回调只挂一次」这个结论不依赖它。

### 4.5.7 补间任务体系：谁推进、谁收尾

| 环节 | 事实 |
|---|---|
| 取任务 | `TextButton@Motion()` = `this.m3.Motion()` —— 取**锚点部件**的 `PartsMotionTask` |
| 设起止 | `SetPos(-300,0,0,0,1)` / `SetAlpha(0,1,0)` |
| 挂回调 | `SetOnFinishEvent(dg)` 只做 `m2 = dg`，它自己**不触发**任何东西 |
| 推进 | `PartsMotionTask@OnUpdate`：**`m1 == -1` 时直接 return** |
| 时钟 | `PE_AdvanceMotionClock(dt)` 只在 `vm_frame_pump` 里调；`dt = now - last_tick`，上限 100ms |
| 收尾 | 两条互不依赖的路：① `m2` 回调（`dg`）；② `PartsMotionTaskList@CheckJoin` → `EndWaitForClick` |

`SceneTurnStart@FadeOut` 只用了 ①：`Overlay.FadeOut(1500, dg = SceneStack@Exit)` 挂的是
`m2`，由 `CASTask` 的完成事件触发，**不经过 `CheckJoin`**。所以「淡出完成」这件事
完全落在补间任务的完成事件上，和 `WaitForClick` 的等待机制是两套东西。

**`m1 == -1` 那条判据要记住**：任务的目标部件一旦失效（切场景、部件被释放），
`OnUpdate` 每帧直接返回，进度永远到不了 1，`m2` 也就永不触发。
表现出来是「动画停住、回调不来」，而不是报错 —— 这类故障只能从
「任务有没有绑上一个活着的部件」去查。

## 4.6 字符出来了但显示方框：先分码表、再分字体

多字节编码的引擎里，「文字没显示」至少有三层，症状却几乎一样：纹理尺寸正常、
字宽正常、位置正常，只有一个占位方块。按顺序排查，不要跳步：

1. **字节切分**：双字节判断是否符合目标编码（GBK 的前导字节范围与 SJIS 不同）。
2. **码表**：把可疑字符单独喂给转换函数，看是否拿到正确的 Unicode 码点，
   还是落到了 `?` / `0`。这一步可以离线做，不必跑游戏。
3. **字体 cmap**：码点对了却仍是方块，就是字体不含该字形。

第三层最容易踩的坑是**拿日文字体渲染简体中文**：日文 Gothic 只覆盖日文汉字集，
常用简体字会成片缺失，而同界面的另一些汉字恰好能显示，看起来像"随机坏掉"。

修复时不要把某个系统的字体绝对路径写进代码。用平台的字体查询接口按语言族
动态取字体（并记得 `.ttc` 需要 face index），保留用户显式指定字体的最高优先级，
查询失败要能退回原来的字体链。这属于平台适配层，不是核心解释器。

## 4.7 「显示标志是 1」不等于「画出来了」

兰斯10 任务地图的菜单（`Game/CommonMenu/MenuContext:7..13`）装载成功、
有坐标、`show=1`，画面上却一个像素都没有。查这种问题，先按四种成因
逐条排除，不要一上来就怀疑引擎架构：

| 成因 | 怎么判 | 本案实测 |
|---|---|---|
| alpha 是 0 | 打 `global.alpha` | `a=255`，排除 |
| 状态选错了 | 绘制读 `states[p->state]`，不是 `states[DEFAULT]` | `ps=0 st=1`，排除 |
| 内容类型没内容 | `st`（1=CG 2=TEXT 9=FLAT）配 `tex`（纹理 handle） | `st=1 tex=1`，排除 |
| 所属 controller 不活跃 | 打 `[ctrl] add-controller active=N nctrl=M` | `active=4`，排除 |
| 被更高 z 的部件盖住 | 列出同帧所有部件按 z 排序 | 整屏部件都 `a=0`，排除 |

把它们全部排除掉，剩下的才是引擎问题。

**这里有个容易漏的坑**：`show` 有两份 —— `global.show` 和 `local.show`。
我们一开始只判了 `global`。加探针时要把**绘制真正读的那一份**打出来，
否则"部件是显示的"这个前提本身就没验证过。

**第二个坑**：`global.z` 不是直接设的，是 **`parent_z + local.z` 累加**出来的。
兰斯10 地图层嵌套很深，实测 `z` 到 **122272**；而菜单只有 1..131。
如果渲染只按 `z` 排（不管 controller），低 z 的菜单就会被高 z 的地图埋掉。
所以查"为什么看不见"时，要一起打 `controller_no` 和 `z` 两个数 ——
排序键是二维的，只看一个维度会得出相反结论。

**判据**：给部件快照加字段时，按"绘制函数读了什么"来加，不是按
"结构体里有什么"来加。这次加了 `a / ps / st / tex` 四个，
每一个都对应绘制里的一条分支，四条排除完只花了两次跑测。

## 4.8 验收标准

1. 构建日志能回答"这个部件是什么类型、多大、在哪、显示吗"
2. 渲染入口每帧都被调用（或有明确的、覆盖全部变更类型的脏标记）
3. 用坐标计算值点击能命中
4. 窗口缩放后，画面与命中都不错位
5. 可疑字符做过「码表 → 码点 → 字形」三层分离验证

## 4.9 一句话

**"不显示"几乎从来不是渲染写错了，而是"没数据"或"没被调用"。**
先把这两件事排除，再去看像素。
