# 第 4 章 呈现与输入

> 前两层让游戏"算得对"，这一层让它"看得见、点得着"。
> 这一层的错误通常不报错，只是**什么都不显示**。

## 4.1 编号体系以游戏为准

凡是"编号 → 含义"的映射，一律以**游戏自己的代码**为准，不看开源实现。

| 编号体系 | 出处 | 常见分歧 |
|---|---|---|
| 组件类型 | 引擎的"类型名"函数 | 开源实现是旧版编号，整体错位 |
| 事件码 | 事件分发表 | 新增了几种事件，序号后移 |
| 部件状态 | 状态名表 | 状态数量随版本增加 |
| 资源类型 | 加载器分派 | 新增格式插在中间 |

症状统一是"**东西建出来了，但按错误的类型处理**"：

- 按钮被当作 `SpinBox` → 尺寸为 0 → 命中测试永远失败 → "点击没反应"
- 文本被当作 `CG` → 找一个不存在的图片 → 显示空白

**判定方法**：把构建日志里的"实际类型"和"类型名表"对齐，一行一行核。

## 4.2 资源格式的版本分叉

同一个扩展名，不同版本的结构可能完全不同，而**加载器往往只实现了其中一个版本**。

真实案例（flat 格式）：

| 版本 | 图形键结构 |
|---|---|
| v < 15 | `count` + `keys[frame]`（每帧一个键） |
| v ≥ 15 | `frames[frame].keys[i]`（每帧**每个图层**一个键） |

加载器两个都解析了，但渲染器只写了 v<15 的路径：

```c
if (local >= tl->graphic.count) continue;   /* v15 的 count 恒为 0 */
```

结果：所有 timeline 被跳过，**每一个界面都不画**，但没有任何报错、没有任何"未实现"。
加载成功、尺寸正确、`show=1`、`alpha=255` —— 一切看起来都对，就是不显示。

**这一类问题的排查方法**：

1. 确认"数据在不在"（打印解析后的结构体字段，不要只打印"加载成功"）
2. 确认"渲染路径走没走"（在绘制函数入口打点，看是 0 次还是 N 次）
3. 两者都对，才是"画了但看不见"（坐标 / alpha / z 序 / 视口）

这三步能把"不显示"从玄学变成二分。

> 教训：`count == 0` 这种"合法的空值"是最难查的，因为它不越界、不报错。
> 凡是"遍历集合"的地方，都要能回答"这个集合为什么是空的"。

## 4.3 谁驱动渲染：这是架构问题，不是 bug

"画面不更新"最常见的原因不是画错了，而是**根本没人让它画**。

三种常见架构：

| 架构 | 谁决定重绘 | 典型症状 |
|---|---|---|
| 脏标记驱动 | 状态变更时置 dirty，主循环见到才画 | 某类变更忘了置位 → 卡在旧帧 |
| 每帧无条件重绘 | 主循环固定画 | 简单可靠，代价是 CPU |
| 事件驱动 | 窗口 expose / resize 才画 | 窗口被遮挡后不恢复 |

如果你按"脏标记"实现，就必须保证**每一类状态变更都会置位**：

- 部件增删
- 部件属性变化（位置、透明度、显示与否）
- 动画帧推进
- **场景压栈 / 弹栈**（最容易被忘的一类）

漏掉任何一类，都会得到"某个界面就是不显示，其他都正常"。

判定方法：在渲染入口统计"每帧是否被调用"。如果某个场景期间一次都没调用，
问题在驱动方，不在渲染方。

> 我在项目里踩过：渲染被 `scene_is_dirty` 门控，而置位它的只有 `scene_set_wp()` 这类少数调用点。
> 没有任何 AIN 代码会为"一个静态对话框压栈"置位，于是窗口永远停在最后一次 3D 画面。
> 改成每帧提交后，这条线才通。

## 4.4 坐标与命中测试

命中测试失败通常有三个来源，按概率排序：

1. **尺寸为 0**（素材没加载成功，但部件建出来了）
2. **坐标系不一致**（部件坐标是"相对父容器"还是"绝对"，缩放前还是缩放后）
3. **层级顺序错**（被上层透明部件挡住了）

坐标换算的坑：

- 引擎按固定分辨率渲染（如 1920×1080），窗口可能是任意尺寸
- 鼠标坐标是**窗口坐标**，命中测试用的是**渲染坐标**
- 两者之间的换算由画面缩放/黑边决定

验证方法：先假设"命中测试是对的，只是坐标错了"，直接点部件的**中心计算值**。
如果点中了，说明是坐标问题；点不中，再查尺寸和层级。

要拿到部件坐标，最省事的办法是让构建日志把 `name / pos / z / size / show` 全打出来 ——
这一次性投入会在后续每次调试里回本。

## 4.5 输入时序

"点了没反应"有时是时序问题：

- 场景刚压栈，事件处理器还没注册完 → 前 1~2 帧的点击被丢弃
- 淡入动画期间输入被屏蔽（这是设计，不是 bug）
- 事件在**下一帧**才派发，而测试脚本点完就截图

自动化测试里要留足等待：等"目标界面已加载"的标志出现，再点击，再等 2~3 帧才截图。

## 4.6 字符出来了但显示方框：先分码表、再分字体

多字节编码的引擎里，「文字没显示」至少有三层，症状却几乎一样：纹理尺寸正常、
字宽正常、位置正常，只有一个占位方块。按顺序排查，不要跳步：

1. **字节切分**：双字节判断是否符合目标编码（GBK 的前导字节范围与 SJIS 不同）。
2. **码表**：把可疑字符单独喂给转换函数，看是否拿到正确的 Unicode 码点，
   还是落到了 `?` / `0`。这一步可以离线做，不必跑游戏。
3. **字体 cmap**：码点对了却仍是方块，就是字体不含该字形。

第三层最容易踩的坑是**拿日文字体渲染简体中文**：日文 Gothic 只覆盖日文汉字集，
常用简体字会成片缺失，而同界面的另一些汉字恰好能显示，看起来像"随机坏掉"。

修复时不要把某个系统的字体绝对路径写进代码。用平台的字体查询接口按语言族
动态取字体（并记得 `.ttc` 需要 face index），保留用户显式指定字体的最高优先级，
查询失败要能退回原来的字体链。这属于平台适配层，不是核心解释器。

## 4.7 验收标准

1. 构建日志能回答"这个部件是什么类型、多大、在哪、显示吗"
2. 渲染入口每帧都被调用（或有明确的、覆盖全部变更类型的脏标记）
3. 用坐标计算值点击能命中
4. 窗口缩放后，画面与命中都不错位
5. 可疑字符做过「码表 → 码点 → 字形」三层分离验证

## 4.8 一句话

**"不显示"几乎从来不是渲染写错了，而是"没数据"或"没被调用"。**
先把这两件事排除，再去看像素。
