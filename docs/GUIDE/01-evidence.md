# 第 1 章 取证

> **原则：先证后猜。每一个"大概是这样"都要变成"这里是证据"。**

> **本章案例全部来自兰斯10（System4 / AIN v12）。**
> 出现的函数名、地址、日志都是这个项目里 `ain_at` / `[dump]` 的真实输出。
> 你可以直接用同名的东西在字节码里 `grep`；换成你自己的引擎时，
> 对应关系通常是一目了然的（`Parts` ↔ 部件、`HLL` ↔ 宿主导出表）。

## 1.1 你要逆向的不是算法

新手最容易走错的一步：以为要读懂游戏的业务逻辑。

不需要。业务逻辑是字节码，跑起来就对了；跑不对通常是**你理解的调用约定和它的实际约定不一致**。

所以要逆向的对象是**约定**，一共四类：

| 对象 | 典型问题 | 证据在哪（兰斯10 里的具体位置） |
|---|---|---|
| 指令语义 | 这条指令弹几个、压几个、有无副作用 | 指令表 + 编译器生成的固定模式（`DG_CALLBEGIN` 之后必是 `[args, dg_page, 0]`） |
| 值布局 | 一个"对象引用"占几个槽 | 方法调用序列的形状（`REFREF → POP → CALLMETHOD`） |
| 类型编号 | "按钮"的组件号是 0 还是 11 | `CBatchRenameStack@GetPartsTypeName` 的 `SWITCH 31` |
| 绑定关系 | 第 N 个 HLL 槽对应哪个 C 函数 | `ain lib:27` 打印的导出表 + `HLL_EXPORT` 宏 |

这四类都有**确定答案**，而且答案就藏在二进制里。不需要猜。

## 1.2 最小反汇编器

不要从零写一个完整反汇编器。你需要的最小集是：

1. **一张指令宽度表**（每条指令占几字节、有几个立即数）
2. **函数地址索引**（`fno -> code offset`）
3. **按函数解，不按地址解**

```c
/* 最小可用版本：只要宽度表正确，就能线性扫完一个函数体 */
for (size_t ip = fn->address; ip < fn_end; ip += width[op]) {
    int op = code[ip] | (code[ip + 1] << 8);
    printf("%08zx  %-20s", ip, name[op]);
    for (int i = 0; i < imm_count[op]; i++)
        printf(" %d", read_i32(code + ip + 2 + i * 4));
    putchar('\n');
}
```

### 血泪：不要从任意偏移开始反汇编

字节码没有对齐填充，指令长度 2~26 字节不等。从中间某个地址开始解，你会得到一串"看起来像指令"的垃圾
（`PUSH 1837465`、`BAD`、莫名其妙的跳转），然后据此得出完全错误的结论。

兰斯10 里真实的翻车现场 —— 想查 `Parts@SetOnClickEvent` 在哪儿调用，从 `0x38d260` 起解：

```
DISASM at 0x38d260 count=12
  0x0038d260: 0x006 INV
  0x0038d262: 0x000 PUSH                               2
  BAD 0x734a
```

`INV` 不是合法指令 —— 说明我算错了入口。这个函数真正的头在 `0x38d246`，
从那儿解就完全正常（第一句是 `PUSHSTRUCTPAGE`）。

**只从函数入口解。** 想知道某个地址附近是什么，先用函数索引查出它属于哪个函数，再从那个函数的
`address` 开始，一路解到目标地址。

这一条我吃过两次亏，两次都浪费了半天。第二次更贵：我拿错误的反汇编去推断"这个委托从来没被注册"，
方向整个错了，绕了三轮才回到原点。

## 1.3 自证型证据：让程序自己作证

最可靠的证据类型是：**程序为了自己使用而维护的映射表**。它不会说谎，因为说谎它自己就跑不对。

### 三种常见形态

**① 名字分发表**

引擎往往有一个"内部编号 → 显示名"的函数，通常是一个 `switch`。

```
switch (component_type) {
  case 0:  return "按钮";
  case 8:  return "レイアウトＢＯＸ";
  case 17: return "ＣＧ";
  case 26: return "フラット";
  ...
}
```

这张表是**权威**的。开源实现里的常量（照抄自旧版本）和它对不上时，以这张表为准。

导出方法：找到这个函数，解析它的 `SWITCH` 指令，把 `case 值 → 目标地址` 全部打印出来，
再到每个目标地址读那条 `PUSH 字符串索引`。

**兰斯10 里的位置**：`CBatchRenameStack@GetPartsTypeName`，一条 `SWITCH 31`。
它给出的表是 `0=按钮 / 8=レイアウトＢＯＸ / 17=ＣＧ / 19=文本 / 26=フラット`，
而 `xsystem4` 上游（旧版）的枚举把 `11` 当 CG。差别就是这一条：
`GetButton("OKButton")` 恒返回 null，因为 `OKButton type=11` 落进了 `SpinBox` 分支。

**② 错误信息**

`"Invalid string index: %d"` 这种字符串会直接告诉你：某个值不是它该有的类型。
把这类信息当成探针的落点，比你自己加十行日志有效。

**③ 编译器生成的固定模式**

编译器对同一段源码会生成**固定的指令序列**。认出这个序列，就能反推源码里的写法。

例：一个结构体构造并返回一个"接口值"，编译器会生成：

```
PUSH 0
DUP_U2
SP_INC
RETURN
```

这串东西说明了返回值的**槽数**和**所有权**（`SP_INC` 是给调用方加引用）。
它比任何文档都可信。

## 1.4 交叉验证：一个结论要两条独立证据

单条证据会骗人（尤其当你解错了偏移）。规矩是：

> **每条结论至少两条证据，来源不同。**

| 结论 | 证据 A | 证据 B |
|---|---|---|
| 接口值占 2 槽，对象在低槽 | 构造函数的 `PUSH 0 / DUP_U2 / SP_INC` | 方法调用序列里 `REFREF → POP → CALLMETHOD` 的栈形状 |
| 组件类型 0 = 按钮 | 名字分发表 `case 0` | 实际构建出的部件能通过命中测试 |
| 泛型返回槽宽由 tag 决定 | 指令表第三立即数的类型 | 空数组调 `Max` 时栈深度的实际变化 |

两条证据都指向同一结论时，才可以写进代码注释。只有一条时，注释里要写"待验证"。

## 1.5 三个反模式

**反模式 1：按名字猜语义。**
`GetFooBar` 不一定返回 FooBar，它可能是个 out-param 形式、返回 bool 的写操作。
**按形状猜，不按名字猜。**

**反模式 2：按常量表猜编号。**
旧版开源实现里的 `enum { CG = 11, LAYOUT = 8 }` 可能是三年前的版本。
编号体系变过一次，所有常量就全错，而且不会报错，只会"按钮点不动"。

**反模式 3：用"崩溃位置"当"bug 位置"。**
`Invalid string index: 4693544` 出现在读数组元素的地方，但真因在
"泛型容器被初始化成了 int 数组"，四层之外。
**崩溃点是症状的终点，不是原因的起点。**

## 1.6 取证记录怎么写

一条合格的记录包含四段，缺一不可：

```
[根因编号] 一句话结论
现象：可复现的观察（日志原文 / 截图 / 数值）
取证：用了什么手段，看到什么（字节码片段 / 内存布局）
判据：怎么确认修好了（可执行的检查）
```

反例（这种记录三个月后没人看得懂）：

> 修了按钮不响应的问题，改了类型映射。

正例：

> **[D119] 组件类型号以游戏自身为准，开源实现的编号不可用**
> 现象：`GetButton("OKButton")` 恒返回 null，`X_ICAST 1078` 的 `ref=-1`。
> 取证：`CBatchRenameStack@GetPartsTypeName` 的 `SWITCH 31` 给出权威表
> （`0=按钮 8=レイアウトＢＯＸ 17=ＣＧ 19=文本 26=フラット`）；
> 而构建日志显示 `OKButton type=11`，落到了 `SpinBox` 分支。
> 判据：`[act] OKButton type=0` + 点击后 `OnClickEvent` 被调用。

**根因编号要跨文档唯一。** 三个月后你会需要"这个 bug 是不是修过"，编号是唯一的索引。

## 1.7 「注册了」和「派发时读得到」是两件事

事件系统卡住时，日志最容易把人带到「委托没注册上」这个结论上：派发端报一个空炮，
于是回头查注册代码。但**空炮只说明读取端那一页是空的，不能反推写入端没写**。

正确的取证姿势是**在两端各打一次身份**：

| 端 | 要记什么 |
|---|---|
| 写入端（`+=` / `AddXxxEvent`） | 目标容器槽号、追加进去的对象、写回后的元素个数 |
| 读取端（事件派发） | 这次取到的容器槽号、遍历到的下标 |

若两端槽号不同，根因是**容器身份漂移**（对象被重建、副本被派发、堆槽被复用），
不是注册失败。这一步能一次排除掉一大半错误方向：
「目标对象被回收」「空成员被丢弃」「点击没命中」「键码传错」全都变成并列嫌疑，
而不是各自试一轮。

配套经验：诊断开关的全局条数上限会被启动期的正常空炮占满，
**长跑一定要带按编号过滤的能力**，否则你要找的那条 MISS 永远不会出现。
写探针时就顺手把过滤参数加上。

## 1.8 告警上万条时：先做直方图，再让释放者自报家门

最吓人的一类现场是同一条告警刷了一万多行。它其实比"偶发一次"更好查：
**数量本身就是证据**——说明一小撮对象被反复误操作，而不是系统性地到处漏。

兰斯10 的移植里，单局打出 13720 条 `double free of slot` 告警，唯一槽号只有 278 个。
按这个顺序收敛，四步就够：

1. **直方图**。在告警点打印指令地址 / 函数号 / 槽号，离线聚合。
   一万行塌缩成 4 个热点地址加一批固定槽号，嫌疑范围从"整个堆"
   缩到"几个 foreach 的收尾"。
2. **单槽全生命周期**。给探针加一个 `WATCH_SLOT=<n>`，只跟一个槽，
   打印 alloc / ref / unref 的地址与调用者。会看到"三次减、两次加"这种
   一眼可辨的不对称，以及**哪一次把 ref 从 1 减到 0**。
3. **让释放者自报家门**。光在 `unref()` 里打调用栈不够——引用计数
   通常是在"容器销毁"时递归释放成员的，调用栈只看得到外层函数。
   要**在遍历容器成员的那一层**打印：容器类型、元素个数、成员下标、
   成员槽号。这一步直接给出"哪个页持有它、却没有自己的引用"。
4. **A/B 验证**。修复带一个可关闭的开关，同序列同指标对照；指标不动
   就回退（见 5.3）。

第 3 步最容易被跳过，也最值钱。本案前两轮都停在"函数返回时多减了一次"，
补上容器现场后才看到：一个 7 元素结构体数组的**浅拷贝副本**在销毁时
释放了原数组的元素，而浅拷贝压根没给元素加引用。

判据清单：

- 告警条数 / 唯一对象数 —— 区分"面状漏"和"点状反复"
- 致命释放（ref 1→0）发生的那一帧，而不是之后的一万次空炮
- 写入端和销毁端是否共用同一套"哪些类型算引用"的判定

## 1.9 判据的采样位置选错，等于没有判据

兰斯10 的部队编成界面上，点击卡片一直进不了 `SceneParty@OnClickCard`(24300)。
我为此连续追了七八轮，每一步都"证据确凿"：

```
XSYS4_FN_DUMP=426  →  ActivityName 只有 Game/Omake/SceneStartScreen
[dgm] MISS dg 1087 →  委托索引越界
XSYS4_DUMP_AT      →  PartyCard.m_cursor.m0 = 0
```

由此写出过三个完整结论：UC 事件派发器从不处理 `Game/Party/*`、
`Parts@SetOnClickEvent` 全网只有一个调用点、卡片点击委托被覆盖。
**三个都是错的。**

真正的原因只有一句：我点的 `(349,157)` 落在顶部那排 **346x174 的图鉴/成就卡**上。
用 `XSYS4_INPUT_DBG` 把候选表按 `parts_no` 一查，人物卡的 cursor 是：

```
parts=900001474 hb=(31,0,208,312) global=(31,420)  click=1 show=1
parts=900001476 hb=(251,0,208,312) global=(251,420) click=1 show=1
```

它们在 **y=420 往下**，和我一直点的位置差了 263 像素。改点 `(135,576)`，
`PartyCard@OnClick`(24226) 和 `OnClickCard`(24300) 立刻各命中 1 次、0 ERROR。

**判据**：在断言"某个回调没被调用"之前，先证明**激励真的送到了它那个对象上**——
打印被点中的 `parts_no` / `global` / `click`，和目标的部件号对一次。
只看到"回调没进"就往上游找原因，会把测试脚本的坐标错误当成引擎的结构性缺陷。

同类第二次：更早我还用屏幕中心 `(960,540)` 统计过"1450 个部件里 0 个可点"，
而那里压着全屏成就模态。**采样点不在目标上，样本再大也没用。**

## 1.10 从症状倒推出来的"原因"，必须先量一次

兰斯10 进部队编成界面的判定链是这样的：

```
SceneQuestMap@CheckNoLeader
  if (g_party._Leaders.IsEmpty())                 ← A
      if (g_playerCard.IsExistPartyAvailable())   ← B
          Scenes::RunParty();                     ← 进编队
      else 弹「没有可编组的角色」
```

看到"进不了编队"，很自然会怀疑 A 或 B。我按这个思路追了两轮：

- `B` 从没被调用过（在 `CALLHLL` 处下的 `DUMP_AT` 一次没命中）
- 于是推断"A 返回了 false，说明有领队"
- 又推断"`m_org` 是空的 → 卡池空 → 没有卡可编组"

**这两条推断都是循环论证**：我用"B 没被调用"去推"A 为假"，
又用"A 为假"去解释"B 没被调用"。全程没有量过任何一个实际值。

真正量一次就一句话的事：

```c
/* 给 DUMP_AT 的 this.mN 补上字符串文本（原来只打槽号） */
[dump] this=slot 2140 type=2 struct=927 nr=10
[dump]   this.m0 = 2141
[dump]     -> str ""                 ← LeaderCard.m_cardId
```

```c
/* Array.Any 的判定与结果 */
[ARR] any nr=7 pred=1 fno=22 -> 1
```

两条读数合起来就是：`m_leaders` 有 **7 个元素**，里面**确实有
`m_cardId != ""` 的真卡**，所以 `IsEmpty()` 返回 false 是**正确行为**，
`CheckNoLeader` 不弹「没有领队」也是正确行为。整条 B 分支走不到，
不是 bug，是前提不成立。

**判据一**：从症状倒推出来的每一环，都要有一个"我量过"的数字。
"应该是空的吧"和"实测 nr=0"之间差着好几轮排查。

**判据二**：连续两次推断互相解释（A 为假所以 B 不走 / B 不走所以 A 为假），
必须停下来量其中一个。互相解释的链条不是证据，是同义反复。

**判据三**：容器类结论要看**元素数**和**元素内容**两件事。
`nr=7` 只说明有 7 个槽；`m_cardId` 是不是空串才说明它们是不是卡。
这两条读数缺一条都会得到相反结论——这次就是先把前者当成了后者。

顺带一个工具习惯：`DUMP_AT` 的 `this.mN` 原来只打槽号，字符串成员
和盲盒一样。补上文本打印（判断在 `page` 分支之前，因为字符串槽的
union 里 `page` 指针是脏的）之后，这类问题从"再追两轮"变成"看一眼"。

## 1.11 验证手段自己被覆盖时，观测等于没发生

这一轮我想验证「点编队卡片会不会触发 `OnClickCard`」。跑测输出是这样的：

```
[inp] pos=(960,540) clicking=0 pulse=0 began=0 prev=0 down=0
[inp] pos=(960,540) clicking=0 pulse=0 began=0 prev=0 down=0
```

指针从头到尾没动，于是结论很自然：「点击没进输入层」「xdotool 点到别的窗口了」
「坐标换算错了」。差一点又开一轮 `xdotool getmouselocation` 的排查。

真实原因在一条被忽略的输出里：

```
unknown step: 45
```

我把动作序列写成了环境变量：

```bash
RANCE10_LIVE_SEQ="wait:22000;click:115,96;wait:3000" \
    ./tools/xsys4 seq pk2 55
```

而 `xsys4 seq` 的签名是 `seq <tag> <序列> [秒]` —— **序列是位置参数，
它会覆盖我传的环境变量**。于是实际执行的是 `RANCE10_LIVE_SEQ=55`，
`55` 被当成一个动作名 → `unknown step` → **整条序列一步都没跑**。

那一刻的输入日志是真的（指针确实没动），推断也是真的（没人点它），
但**前提是假的**：点击根本没被发出。

**判据一**：动作序列、探针开关这类「我以为是自己在控制」的东西，
跑完先确认**它真的生效了**，再解释它的输出。最省事的办法是让它自己报一句：

```
unknown step: 45          ← 只看一行就能否掉整轮实验
OK click at 963,817        ← 点之前先打印换算结果
CLICK view=115,96 win=115,96 ptr=x:115 y:96
```

**判据二**：日志里出现「未知/未识别/跳过」这类词时，先当它是**自己配错了**，
不要当成被测物的问题。`unknown step`、`skip click`、`not found` 都属于同一类。

**判据三**：**位置参数和环境变量同名/同义时，一律以位置参数为准**。
写跑测命令时二者只用一个，不要「两边都传，指望有一个生效」。

同一轮里还有第二个同型陷阱：`(963,817)` 这个坐标一度被我当成「我的点击落偏了」，
其实是脚本自己用来打发网络确认框的固定 OK 按钮坐标。**先分清「谁发的点击」，
再讨论「点到了哪」** —— `XSYS4_CLICK_DBG=1` 会把每次点击的 view/win 坐标一并打出来，
一眼能对上账。

## 1.12 全局单例被覆写时，症状会伪装成别的模块

兰斯10 编队界面跑起来之后立刻崩，报的是：

```
[Error] AsraFramework 内部错误 / CASTimerManager - 句柄错误
  at CASTimerManager@CheckHandle <- CASTimer@Get <- view::detail::CalcPassedTime
*WARNING* double free of slot 78 (VM_PAGE)
```

按症状找，最自然的两个方向是「`Array.At` 的引用返回写错了」和
「`CASTimer` 的句柄表被谁清空了」。两个都查了，都不对。

真实链条离它十万八千里：

```
Array.Alloc(m1, 71, 24, -1, -1)   tag=AIN_ARRAY
  -> 旧实现把第二维 24 当成元素类型，只造 array nr=71 [0,0,0,...]
  -> QuestMapObjectCollection@0 执行 m1[X][Y] = index
  -> m1[X] = 0，而 **0 是 GLOBAL_PAGE 的堆槽**
  -> 赋值落到 heap[0].values[Y]
  -> global[14]（CASTimerManager 单例）从 95 被写成 2,3,4,7,18,20...
  -> 定时器拿到的不是 manager -> 「句柄错误」-> 场景退出 -> double free
```

一个**地图二维网格没建内层数组**的错，表现出来是「定时器句柄失效 + 场景崩溃」。
中间隔了四层，靠读症状永远猜不到。

### 怎么把它挖出来

**第一步：量「症状的直接原因」，但别停在那儿。**
`CheckHandle` 里 `At(m1,40)` 返回空引用，现场 dump：

```
this.m0 = array nr=42 [115 131 139 152 ...]   ← 别的 manager
this.m1 = array nr=0                          ← 空
l0 nHandle = 40
```

一开始我以为是 `At` 的引用解析坏了。加探针才发现 `At` 本身
**1862 次失败但都有正当理由**（数组为空 / 下标 -1），指针反解在能
解析时全是 `resolved=1`。**症状的直接原因成立，但不是根因。**

**第二步：盯「不该变的东西」什么时候变了。**
给 ASSIGN 加一个只在**值发生变化**时打印的探针：

```
[g14] ip=0x459F24 old=95 new=2
  0x00459f24 in QuestMapObjectCollection@0
  0x0045648e in QuestMap@Init
  0x00372eb2 in SceneQuestMap@0
```

这一行把两者接起来了：写入者根本不在定时器模块里。

**第三步：看声明，不要看数值。**
`global[14]` 声明是 `data=13 struc=5`，也就是 `CASTimerManager`。
而写进去的是 2、3、4、7、18… 递增的地图对象序号。
**类型对不上的那一刻，就说明写错了对象**，不用再往下猜。

### 三条判据

**判据一**：一个模块**突然**报错、而它自己的数据结构看起来「空了」，
先问「是谁把它换掉的」，不要只问「它为什么读不到」。
本项目里 `heap[0]` 是全局页，**任何取到 0 的引用都会静默落到全局变量上**——
这是这类 bug 的高发地形。D106 在 `variable_initval` 侧见过一模一样的形状
（`global[67][i]` 覆写 `globals 0..39`），几年后又在 `Array.Alloc` 侧复发。

**判据二**：探针要能回答「什么时候变的」，而不只是「现在是多少」。
只在值变化时打印、并附调用栈，比全量快照有用得多。
另外**别给全量探针设小上限**——第一版 400 行正好把要看的那条切掉了，
我又误判了一轮（见 1.11）。

**判据三**：修完要做「流程深度不变」的对照，不能只看错误数归零。
这次 A/B：

| | acts | AIN Error | double free | Party 活动 |
|---|---|---|---|---|
| 关 | 108 | 268 | 2 | 101 |
| 开 | 107 | 0 | 0 | 101 |

`Party=101` 两边一样，才说明是「消掉了根因」而不是
「把流程提前掐断所以没机会报错」。
