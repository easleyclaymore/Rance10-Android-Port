> **以《兰斯10》Linux 移植为唯一案例的复盘**
> 版本 1.0 · 2026-11-15 · 写给不懂实现语言的项目管理者
> 依据范围：2026-11-07 ~ 11-15 的工作日志、D1xx–D202 根因记录、README / TECH_DEBT / GUIDE / SDK 四组文档、提交历史与进度汇报

## 0. 先说结论

这个项目没有需求文档、没有源码、没有可以问的人，只有一份成品游戏的字节码和一套不完整
的开源旧实现。在这种条件下，团队把「跑到哪个界面」从**标题画面**推进到了**第一章剧情脚本
真的执行**，过程中没有出现一次「改好了但不知道为什么」的交付。

支撑它的不是某个聪明人，而是一套**专门用来对抗"自欺"的管理体系**：

> 每一轮先写清楚「怎样算修好了」，再动手；
> 每个结论必须有两条独立证据；
> 每次改动都要能在同一条固定流程上，用同一个数字证明它真的变了；
> 结论被推翻时公开记录，而不是悄悄改掉。

**如果你只记五条**：

1. **判据先于行动**。没有「怎样算好」的问题不许开工。
2. **零错误不是通过标准**。本项目多次出现「日志干净 + 画面全黑」。
3. **观测工具也是被测对象**。这本书里一半的错误结论，是自己的探针给的。
4. **结论可以被推翻，而且要留痕**。推翻本身是进展，不是失败。
5. **知识只允许有一个存放位置**。两份相同的文档，等于没有文档。

### 你（管理者）最该做与最不该做

| 该做 | 不该做 |
|---|---|
| 每次开工问「判据是什么」，而不是「什么时候能好」 | 要求用百分比报进度（本项目用「能跑到哪个界面」） |
| 问「这个结论有几条独立证据」 | 把「日志没有报错」当成验收 |
| 保护「证伪也要写进台账」的文化 | 删掉看起来没用的历史记录 |
| 管住范围：一轮只攻 1–2 个问题 | 同时开多条战线、催并行 |
| 给稳定的跑测环境与固定的时间盒 | 让不懂细节的人拍板技术方案 |
| 把「看起来正常」从验收词表里删掉 | 用周报代替状态文档 |

> 你不需要懂 C。你需要懂的是：**什么样的回答算证据，什么样的回答只是安慰。**

## 1. 先把词说清楚

下面每个词在后面都会反复出现。右边一列说明「为什么管理者要懂它」——你不需要会写，
但需要能判断别人有没有做到。

| 词 | 大白话 | 在本项目里的具体样子 | 你为什么要懂 |
|---|---|---|---|
| **黑盒** | 只有成品，没有源码和说明书，只能从外面观察行为 | 手里只有游戏数据和一份旧版开源引擎 | 决定了「问人」和「查文档」都不存在，只能靠实验 |
| **字节码 / 反汇编** | 游戏逻辑被编译成一串编号指令；把编号还原成可读清单叫反汇编 | 约 3 万个函数，靠 `ain_at` / `ain_xref` 等离线工具读 | 「读代码」在这里是取证的起点，不是改代码 |
| **解释器（VM）** | 我们写的那个「照着编号做菜」的程序 | `xsystem4`，用 C 写 | 团队真正在交付的产品，不是游戏本身 |
| **HLL** | 字节码能调用的「外部能力清单」：画图、存档、放声音 | 36 个库、上万个导出项；未实现会直接中止流程 | 用它做「能力覆盖率」，是少有的可量化进度 |
| **探针** | 临时插在程序里、把内部状态打到日志的记录员 | `XSYS4_*` 环境变量，默认关闭 | 探针会撒谎，是本项目的头号误判来源 |
| **日志** | 程序运行时写下的流水账 | `[call]` `[parts]` `[flat]` `[ctrl]` 等前缀 | 日志前缀相当于团队内部的接口，改格式等于破坏协作 |
| **判据** | 一条能明确回答「好了没有」的检查，最好能自动执行 | `23487` 命中、`acts=111`、`Unimplemented HLL = 0` | 你验收时唯一该看的东西 |
| **基线** | 一套固定动作 + 一组固定数字，每次改完都跑一遍 | `acts=111 / err=0 / core=0 / party=101`（写作当日快照，现值见 `docs/STATS.md`） | 没有基线，就无法区分「改进」和「碰巧」 |
| **回归** | 改了 A，却把已经好的 B 弄坏 | 编队进出闭环每次都要重跑 | 「完成」的定义里必须包含它 |
| **A/B 开关** | 同一个程序，用一个环境变量决定走新逻辑还是旧逻辑，其他全不变 | `XSYS4_ABS_ALL=1`、`XSYS4_FIX=0` | 这是本项目最省钱、最科学的实验手段 |
| **门禁** | 交付前自动跑的一套检查 | `./tools/xsys4 check`、`check_core_deps.py` | 把纪律变成工具，才不会靠自觉 |
| **工作树 / 提交** | 还没归档的代码改动 / 归档成一个可追溯的版本 | 功能未完成就留工作树不提交 | 决定风险：多久没备份、能不能回滚 |
| **技术债 / 冻结债** | 明知不完美但先记下来；冻结＝明确决定不修并写下理由 | `TECH_DEBT.md` 的 A / B / C 三组 | 让「没做完」变成可管理的清单，而不是遗忘 |
| **根因编号（D 号）** | 给每个查明的根因一个跨文档唯一的编号 | D131、D161、D199、D202… | 三个月后回答「这个坑是不是踩过」的唯一索引 |
| **序列化** | 把内存状态写成文件（存档），字段顺序固定 | 存档格式对 `struct parts` 加字段极敏感 | 解释为什么「加个字段」这种小事会被禁止 |
| **覆盖率** | 清单里「已实现」占「总共需要」的比例 | HLL 真实现 2,151 / 3,351（64%，2026-11-15 实测） | 少数能对外解释的硬数字之一 |
| **里程碑** | 带验收判据的阶段目标 | 标题出画 → 地图出画 → 编队闭环 → 剧情链 | 汇报里最不该省的是「怎么验」，不是「哪天完」 |

## 2. 体系全貌

```
                    ┌──────────────────────────────────────────┐
   状态层（现在）    │ README §0 / TECH_DEBT.md                  │  每次会话开场必读
                    │ 阶段 · 最大卡点 · 本轮 1–2 件事 · 判据    │  只写结论，不写过程
                    └──────────────────┬───────────────────────┘
                                       │ 决定「这轮做什么」
                    ┌──────────────────▼───────────────────────┐
   执行层（这一轮）  │ 取证 → 假设 → A/B 实验 → 修复 → 回归     │  四条流水线，见下
                    └──────────────────┬───────────────────────┘
                                       │ 产出「证据 / 结论 / 判据」
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
   ┌──────────────────┐   ┌────────────────────┐   ┌────────────────────┐
   │ 知识层（永远）    │   │ 状态层（更新）      │   │ 归档层（过去）      │
   │ docs/GUIDE/       │   │ README / TECH_DEBT  │   │ archive/  只读     │
   │ 可复用方法论      │   │ 债已清零 / 新卡点   │   │ 全文、取证链、     │
   │ 不随项目状态更新  │   │ 契约编号            │   │ 多轮误判过程       │
   └──────────────────┘   └────────────────────┘   └────────────────────┘
```

**四条流水线**（每一轮都完整走一遍）：

1. **取证线**：离线工具读静态数据 → 日志探针读运行时状态 → 至少两条独立证据
2. **实验线**：新逻辑做成默认关闭的开关 → 同一序列跑 A/B → 只比一个计数型指标 → 跑默认基线回归
3. **交付线**：临时探针删除 → 开关登记 → 门禁 → 提交（信息里写根因、证据、验证）
4. **沉淀线**：结论进状态文档 / 方法论进 GUIDE / 过程进 archive / 编号 D 串起三者

> **一句话**：状态文档管「现在」，知识文档管「永远」，归档管「过去」。
> 三者职责不重叠，才不会出现「同一个结论在四个地方、四个版本」。

### 为什么这份手册现在只有一个 GUIDE

2026-11-15 之前，方法论书同时存在两份：工作区 `GUIDE/`（写作副本）与仓库
`docs/GUIDE/`（发布副本），靠一句「改完必须 `cp` 同步」的口头约定维持。
复盘时发现两份已经不一致：仓库版多了三条探针纪律、更新日志已重排，工作区版是旧的。

这是**单一信息源（Single Source of Truth）**被破坏的典型：只要允许两份并存，
就必然出现「哪份是最新的」这个问题，而答案只能靠人记。处理方式不是补一句更严厉的
约定，而是**物理删除一份**、把剩下那份的路径写进所有引用处。

## 3. 复盘：实际跑过的十二条制度

每条按「做法 → 出自哪次实践 → 你该盯什么 → 什么时候会失效」四段写。

### 3.1 会话启动仪式：开场三句话，一轮只攻 1–2 个问题

**做法**：每次开工先答三件事——① 当前阶段（哪条链能跑、跑到哪个界面）；
② 最大卡点（台账 A 组第一条）；③ 本轮要做的一两件事 + 判据。然后**只做这两件**，
不加载全部历史。

**出自实践**：2026-11-13 写入长期约定。起因是长会话里反复出现「顺手又查了三个方向」，
结果每个都停在半截，状态文档反而对不上现场。

**你该盯什么**：会议开场能否在 30 秒内说清这三句；「本轮只做两件」是否写进了状态文档。

**会失效于**：多人并行、多条战线同时推进时——那时需要看板与在制品（WIP）限制，
不是一句口头约定（见 §6）。

### 3.2 判据先行：先写「怎样算修好了」，再动手

**做法**：每轮状态文档里的「判据」一栏必须是**可复现、可判定**的，例如
「`23487` 命中 + `Game/Adv/*` 装载 + 运行期 `Unimplemented HLL function = 0`」，
而不是「按钮能正常显示」。

**出自实践**：GUIDE 第 5.1 节把判据固化成三条互相独立、缺一不可的指标：
栈平衡（内部账目对不对）、差分对照（这次改动到底改变了什么）、出画（端到端真的通了）。
第 5.4 节甚至把「有画面」量化成截图文件大小 + 灰度均值：
`mean ≈ 0 且文件 < 1 KB` 就是纯黑，`> 1 MB 且 mean 在 0.1~0.6` 才算有内容。

**你该盯什么**：判据里有没有数字、有没有可执行命令；「看起来正常」出现一次就该打回。

**会失效于**：判据是人眼判断时（见 §5.1、§6.2）。

### 3.3 三层文档分工与体积纪律：任何一次读文档都不超载

**做法**：只维护三处——`README.md`（现状/契约/开关/纪律/文档地图）、
`TECH_DEBT.md`（未结债 + 极简已清零索引）、`docs/GUIDE/`（方法论，不随项目状态更新）。
其余一律进 `archive/` 且只读，**不按日期新建阶段报告**。
README 目标 ≤ 250 行；单条排障叙述不超过 3 行；每次瘦身前先把全文 `cp` 到 archive，不丢证据。

**注**：「只维护三处」是写作当时的约定；现行分工已扩展为四处状态文档 + 仓库内工具链 /
台账 / 生成物，**以工作区根 `../README.md` §5–§6 的文档地图为准**，不要再按本段判断。

**出自实践**：2026-11-13 把 README 从 1056 行 / 80K 压到 215 行 / 16K，
TECH_DEBT 从 118 行 / 40K 压到 82 行 / 12K。压掉的不是信息，是**读取成本**：
证据链移到 archive，方法论移到 GUIDE，状态文档只留结论。

**你该盯什么**：`wc -l` 和最长行；有没有人又开始写「本轮工作总结.md」。

**会失效于**：团队扩张后，一份 README 装不下多个小组的状态——那时应拆成
「项目状态 + 各小组看板」，但**仍要保持每份文档只有一个职责**。

### 3.4 根因编号 D 与四段式取证记录

**做法**：每个查明的根因给一个跨文档唯一编号 `D<数字>`。一条合格记录必须四段齐全：
**结论 / 现象（日志原文或数值）/ 取证（手段 + 看到什么）/ 判据（怎么确认修好了）**。

**出自实践**：GUIDE 1.6 节给了一正一反两个例子。反例是「修了按钮不响应的问题，改了类型映射」——
三个月后没人看得懂；正例带组件类型号、`X_ICAST` 错误值、权威映射表来源和可复现判据。
D 号现在串起 README 契约、TECH_DEBT 清偿条件、工作日志与提交信息（如 `fix(d202):`）。

**你该盯什么**：提交信息里有没有编号；问「这个坑以前是不是踩过」时能不能 1 分钟查到。

**会失效于**：编号只记「根因」不记「决策」。本项目多次出现「试了 A、退回、改走 B」
（如 D165 试实现 `SetEnableInputProcess` 后主动退回），这类**为什么放弃**的知识没有专门字段，
只能散在日志里（改进见 §6.8 ADR）。

### 3.5 技术债分级：A 结构性 / B 会炸的 / C 长尾

**做法**：台账只列**未结**项，按「错一处炸一片→当前不挡路但随时引爆→冻结记账」排序。
每条只写「现象 → 清偿条件」，不写修复过程。已清零项做成极简索引
（现象 → 根因 → 契约编号/位置），并明确哪些是**冻结债**（决定不修、写下理由）。

**出自实践**：`[HACK-POC]` 232 处标记没有偷偷删掉，而是记成「只加断言不改逻辑，
等能跑到结局后集中清算」；`[MENU-INVISIBLE]` 被标注「已收窄，非渲染问题」，
把后来者从一条死路上拦回来。

**你该盯什么**：每笔债有没有「清偿条件」；有没有债既没修也没写冻结理由。

**会失效于**：清偿条件写成「以后再看」——那等于没有条件。

### 3.6 结论公开推翻：把「我错了」当成一等产出

**做法**：新证据推翻旧结论时，不改口、不抹掉，而是在台账里明确写「已推翻 / 已证伪」，
并把误判过程归档、把教训回流到方法论书。

**出自实践**：本项目最贵也最有价值的一段。
D192 判定「選択肢按钮没有几何」→ D193 推翻（按钮 428×170、能点、能推进流程）
→ D194 判定「被面板盖住」→ D195/D196/D198 建立三种坐标模型
→ **D199 一次性证伪六种模型**：原因是探针「每个部件号只打一次」，
拍到的是容器滑入动画的第一帧（`305` 的 pos 走 0→585→-73→0，
`306` 相应 1920→1262→**1335**），稳态坐标本来就是对的。
六轮工作全部建立在一份错误快照上。

**你该盯什么**：台账里有没有「已证伪」条目；被推翻的假设有没有留下「为什么当时会信」。

**会失效于**：把推翻当成事故追责——那样下次就没人写「我错了」，你会失去最贵的信号。

### 3.7 双证据原则与可证伪假设

**做法**：每条结论至少两条**来源不同**的证据（例如：反汇编里的常量表 + 实际部件的命中测试）。
每个假设要写成能被一次实验否掉的形式：不问「是不是渲染有问题」，
而问「如果渲染没被调用，那 `scene_render` 的调用计数应为 0」。

**出自实践**：`[inp]` 探针的教训被写进长期约定——
「判断功能是否坏，至少要有第二个独立证据（截图 / 外部工具 / 返回值）」。
GUIDE 5.6 节直接列出「坏假设 / 好假设」对照表；5.7 节补了一句最刺人的：
**「零错误」不是通过标准，我见过多次「零错误 + 全黑」的状态。**

**你该盯什么**：汇报里出现「应该」「可能是」时，追问「什么结果会证明你错」。

### 3.8 单变量 A/B + 默认基线回归

**做法**：修复先做成**默认关闭**的环境变量开关，确认收益与代价后再翻转默认；
对照必须同一序列、同一超时、同一截图点，**只比一个计数型主指标**；
每次改动后跑一次默认基线（`acts / err / core / party` 四个硬数字）+ 一条端到端闭环。
对照前先清掉所有诊断变量——取证期随手设的开关会继承到子进程，两组跑的就不是同一个程序。

**出自实践**：GUIDE 5.3 节。最有名的一次是补完引用计数后，告警数
**13720 → 13720**，连热点地址分布都逐条相同。这个「一模一样」比「变差了」更有信息量：
说明改动根本不在那条执行路径上，正确动作是**立即回退**、把证伪写进台账，
而不是把看起来合理的代码留在工作树上继续堆假设。
另一条是「先验证那把尺子」：基线脚本曾把计数写成 `grep -ac ... || echo 0`，
`grep -c` 无匹配时会输出 `0` 但返回非零，于是又补一个 `0`，指标凭空多一行。

**你该盯什么**：A/B 有没有「只改一个变量」；主指标变没变；默认基线四个数有没有对齐。

**会失效于**：截图时机不同。D198 曾把「30 秒后的纯色画面」当成回归，
做同口径对照后发现**默认模式在 30 秒同样变黑**——那是跑测结束清屏。
这类「测量方法本身引入的差异」是 A/B 最隐蔽的敌人。

### 3.9 探针也是被测对象：可观测性纪律

**做法**：探针 / PoC 允许，但必须登记、交付前删除；常驻诊断统一用
`XSYS4_*` 环境变量且默认关闭；开关说明人工维护在 `tools/switch-desc.txt`，
由脚本自动生成 `docs/SWITCHES.md`。

**出自实践**：这是本项目踩得最多的一类坑，已沉淀成 GUIDE 5.5 整节：

| 骗法 | 真实事件 |
|---|---|
| 「前 N 条」限流被先出现的对象吃满 | 排查選択肢按钮时 40 条全打在背景部件上，「没输出」被误读成「没发生」 |
| 全局计数把目标部位挡在门外 | `[tl]` / `[layer]` 探针被 `900000041` 吃满，差点判定「渲染函数没被调用」 |
| 单次快照 ≠ 稳态值 | D199 六轮误判的总根因（见 §3.6） |
| 只打结果、不打设置动作 | 据 dump 里 `pos=(0,0)` 判断「SetPos 没生效」，实际设置发生在快照之后 |
| 全局 dump 的标签 ≠ 归属 | 把另一活动的角标部件当成選択肢按钮，得出「按钮全是 0x0」 |
| 输出缓冲区被复用 | 同一条日志里两次调用格式化函数，两个 `%s` 打出相同内容 |
| 工具本身被硬限流 | `ain_xref … calls` 只扫前 400 个调用点，得出「战斗路径 0 个 HLL」的错误结论（D197） |

**你该盯什么**：新增探针有没有「按对象 ID 去重 / 定向过滤」；交付前是不是真删干净了。

### 3.10 门禁、诚实标注与「不阻塞」的设计智慧

**做法**：「重构完成」有硬定义——**编译通过 + `check_core_deps.py` PASS + 端到端跑一次**。
开关说明表有句很妙的规定：「只写你确实知道的，不知道就留空，
让生成器标成 `—`（那是诚实的债）」。`check --strict` 才把未标注开关判为失败，
默认只警告，源码注释写明了理由：**「否则每次 check 都失败，很快就会被无视」**。

**出自实践**：这句注释值得单独讲给管理者听——门禁的价值不在于严格，
而在于**每次失败都值得处理**。一个长期红灯的检查，三天后就等于不存在。
同理，`save.c` 顺序序列化导致「不能给结构体加字段」这条约束，
逼出了「用旁路表存状态」的一致做法（复选框、消息窗口文本都是这么实现的）。

**你该盯什么**：门禁有没有长期红灯；「通过」是不是靠人手工判断。

### 3.11 提交与分支纪律

**做法**：功能未完成留工作树、**不提交**；完成后按「代码修复 / 清理与文档」分组提交，
提交信息写清根因、证据、验证结果；`main` 是交付分支，实验不推；
子模块若无远端推送权限，改动导出成 `patches/*.patch` 入库并在 README 写明 apply 步骤，
**绝不用 gitlink 记一个别人拉不到的本地提交**。

**出自实践**：2026-11-14 推送 `386fb7e..65c26d1` 三个提交时，
发现 `subprojects/libsys4` 的远端是上游仓库、无写权限。
若按常规把本地提交记进指针，别人 `git submodule update` 会直接失败——
整个仓库对他人不可克隆。改成「子模块回退到上游 commit + 补丁入库」，
并用 `git apply --check --reverse` 验证补丁与工作树完全一致。

**你该盯什么**：提交信息能不能当事故报告读；有没有「为了干净」把失败实验悄悄抹掉。

### 3.12 风险、汇报与「静态清单」优先

**做法**：能用静态清单回答的问题，不要用逐个试探回答。对外汇报用六个硬数字 +
分维度完成度 + 时间线 + 当前卡点证据 + 技术债全景 + 甘特路线 + 里程碑验收表 + 风险分档。

**出自实践**：D197 是最好的例子。管理者担心「点进战斗后满屏未实现函数」，
提议用工具逐个反汇编战斗函数、提前列专用库清单。**方向对，做法可以换**：
引擎的未实现清单是链接期静态的，字节码里的调用点也是静态的，
两边求交集就是全集，不需要猜哪些函数属于战斗。
结果：36 个库 / 11,653 个调用点 / 1,443 个函数，
「会被调用但没实现」553 个函数、785 处；战斗路径两种口径交叉验证后，
真正会撞上的只有 `String.ReplaceRegex` 一个，**当天补完**。

**你该盯什么**：汇报里每个数字有没有口径说明；里程碑表有没有「怎么验」这一列；
风险有没有分档。

> 那条被忽略很久的 `WARNING` 也值得记：D200 发现按钮画不出的根因是
> 图形藏在 flat 文件的 TALT 段（QNT 图集），而解析器一直只打印「不是 AJP 格式」的告警、
> 从不提取数据。**长期存在的噪音里可能就藏着答案**——定期检查被自动忽略的告警，
> 是一条便宜的管理动作。

## 4. 为什么这套方法是对的：它对应哪些科学原则

| 科学原则 | 项目里的做法 | 防住了什么 |
|---|---|---|
| **可证伪性** | 假设写成「若 X 则计数应为 0」；判据先行 | 防止「怎么都说得通」的假设无限消耗 |
| **控制变量** | 单变量 A/B 开关、同一序列、只比一个指标 | 防止把碰巧好转当成因果 |
| **测量工具自检** | 「先验证那把尺子」；探针也是被测对象 | 防止错误的观测反复制造错误结论 |
| **独立复现** | 每条结论两条不同来源的证据 | 防止解错偏移、看错快照 |
| **负结果也要记录** | 证伪写进台账、推翻公开留痕 | 防止同一条死路被走第二遍 |
| **最小假设 / 分层** | 五层结构，下层没验证不往上调 | 防止在渲染层查三天、真因在内存布局 |
| **单一信息源** | 三处文档各管一件事；删除重复副本 | 防止「哪份是最新」靠人记 |
| **反馈回路** | 会话开场三句 → 状态文档 → 下轮判据 | 防止长会话里目标漂移 |

### 适用边界（很重要）

这套体系是为**「极高不确定性 + 单人/单智能体 + 长会话 + 几乎没有自动化测试」**
优化的。它的强项是「在没有说明书时不把自己骗了」。

它**不自动适用于**：

- 需求明确、有完整测试套件的常规项目——那里 CI 与测试用例比手工 A/B 便宜得多；
- 3 人以上并行改同一份代码——口头「本轮只做两件」会被并发冲掉；
- 需要向外部审计交付证据的项目——工作日志 + 归档不构成正式的验证记录。

换句话说：**先判断你的项目有多"黑盒"，再决定照搬多少。**

## 5. 诚实评估：这套体系的十个缺口

下面每一条都在本项目里造成过真实损失。写在这里不是为了否定体系，
而是因为「复盘」若只写好话，就没有管理价值。

| # | 缺口 | 真实代价 | 根子 |
|---|---|---|---|
| 1 | **判据靠人眼看截图** | D198 把清屏当黑屏回归；D199 六轮误判源于单次快照。固定秒数抓屏还会因两条流程时序不同得出假对照 | 判据没有变成「断言」，而是「观察」 |
| 2 | **没有自动化回归 / CI** | 每次改动靠手工跑一条固定动作序列 + 肉眼看四个数字；一次完整验证几分钟到几十分钟 | 黑盒、无预期输出（Oracle），写自动断言成本高 |
| 3 | **临时探针而非结构化事件流** | 限流、静态缓冲、快照时机、标签归属……七类骗法反复出现，每次都要重新设计打印方式 | 日志是人读的文本，不是可查询的数据 |
| 4 | **没有时间盒 / 停止规则** | 一个坐标问题连攻 D193–D199 共六轮，全部建立在错误快照上；中途没有任何机制强制「停下来重新验证工具」 | 「不要随便停下」的文化缺少配套预算 |
| 5 | **假设没有登记** | 多轮里同时存在「没几何 / 被盖住 / 坐标绝对 / 容器根」多个假设，互相污染，事后靠日志才能还原 | 只有结论台账，没有假设台账 |
| 6 | **知识靠人工维护，数字会腐化** | 同一份开关数量在三个文档里分别是 96 / 116 / 136；两份 GUIDE 内容不一致 | 手写数字 + 双份文档 |
| 7 | **指标偏过程，不直接反映可感知进度** | `acts=111 / err=0` 很稳，但「玩家能玩到第一章第几句」没有量化；对外汇报只能靠估算「可玩度 22%」 | 缺一条结果指标 |
| 8 | **风险表静态** | 进度汇报有高/中/低分档，但没有负责人、触发阈值、应对预案；也不随每周更新 | 风险被当成汇报素材，不是管理对象 |
| 9 | **长时间把未完成代码留在工作树** | 「功能未完成不提交」保证了提交整洁，但一旦环境丢失，十几轮实验代码没有任何版本记录 | 提交纪律缺少「临时快照」这一档 |
| 10 | **改动前没有影响面清单** | 曾计划改全局坐标语义，台账后才补一句「会波及所有场景」；这类改动本应在动手前先列影响面 | 缺 blast radius 检查 |

## 6. 更好的做法（按性价比排序）

按「解决哪个缺口 / 最小可行动作 / 成本 / 边界」给。这里的建议是**有取舍的**：
下面几条不是都该做，前三条才是这个项目当前最划算的。

| 方法 | 解决 | 最小可行动作（不需懂 C 也能推动） | 成本 | 边界 |
|---|---|---|---|---|
| **① 假设台账（Hypothesis Ledger）** | 4 / 5 | 一张三列表：`假设 / 能证伪它的一次实验 / 结论（成立·否掉·待验）`。每轮开工前填、收工前结。与 D 号并列编号 | 极低 | 团队一大就要放进共享文档，不能留在个人日志 |
| **② 判据可执行化** | 1 / 2 | 把状态文档里的判据逐条改写成一条命令或一个脚本：断言「日志中出现 X」「某字段等于 Y」，而不是「截图有画面」。先做 5 条最常用判据 | 低 | 像素级「画面对不对」仍需人眼，别强行自动化 |
| **③ 时间盒 + 停止规则** | 4 | 每个卡点给预算（例如「最多 3 轮 / 2 小时」）；到点强制停下，先回答「我的观测工具可信吗」，再决定续做或换方向 | 极低 | 需要管理者顶住「再试一次」的诱惑，这是纯管理动作 |
| ④ 结构化 trace | 3 | 探针统一输出 `时间 / 事件名 / 对象 ID / 值 / 来源`，落盘成逐行 JSON；配一个按 ID 查询的小工具。不再用「前 N 条」限流 | 中 | 值得做，但要等探针形态稳定，否则会反复改 schema |
| ⑤ 轻量 CI | 2 | 每次提交自动跑：构建 + 核心依赖检查 + 一条固定动作序列 + 四个基线数字断言。失败即阻止合并 | 中 | 不建议追求完整测试金字塔：黑盒项目没有预期输出，写大量用例不划算 |
| ⑥ 变更影响面清单 | 10 | 改动前写三行：`会影响哪些场景 / 哪些已有闭环必须重跑 / 若失败怎么回退`。全局语义改动必须填 | 极低 | 大改动才需要，小修补别加负担 |
| ⑦ 结果指标 | 7 | 在四个过程数字之外加一条「玩家可感知进度」：例如「可连续推进的剧情句数 / 已进入的场景数」，每周更新一次 | 低 | 口径要写死，否则又会变成主观估算 |
| ⑧ 风险登记册 | 8 | 每条风险补三列：`负责人 / 触发阈值（什么信号出现就升级）/ 预案`。双周回顾一次 | 低 | 风险不超过 10 条，否则没人看 |
| ⑨ ADR 决策记录 | §3.4 的延伸 | 在 D 号之外，给「为什么选 A 不选 B」「为什么退回」单独一份短记录，每条 5 行 | 低 | 只记重大且不可逆的决策，别记日常 |
| ⑩ WIP 快照分支 | 9 | 每天收工把工作树推到一个个人 WIP 分支或打一个本地快照；正式提交仍保持整洁 | 低 | 别把 WIP 分支当成交付物，也别混进 `main` |
| ⑪ 文档数字自动生成 | 6 | 所有「共 N 个」的数字由脚本生成或直接写「以生成结果为准」，禁止手写 | 极低 | 已在开关表部分做到，推广到其余文档即可 |

### 最小可行第一步：只做三件事

如果只推得动三件，选 **①②③**。理由是它们分别消掉本项目最大的三类浪费：
被自己的观测工具骗、在一条错路上连攻多轮、以及「修好了」无法复核。
而且三件都不需要新增代码能力，**管理者自己就能立规矩**。

### 不建议照搬的

- **重型阶段门 / 详细甘特排到每天**：本项目的不确定性高到「下一轮做什么由上一轮的证据决定」，
  排到日只会制造虚假的确定感。汇报里的 W1–W10 甘特用于对外沟通可以，
  用于内部考核不行。
- **完整测试金字塔（单元 / 集成 / 端到端全覆盖）**：没有规格、没有预期输出，
  大部分「单元测试」测的是自己对字节码的猜测，会把猜测固化成约束。
- **同时启用全部①③④**：工具改造和流程改造一起上，会让团队在两周内既没产出也没新流程。

## 7. 管理者操作指南

### 每次开工，问这五句

1. 现在**能跑到哪个界面**？（不要用百分比回答）
2. 最大卡点是什么，**判据**是什么？
3. 这轮做几件事？（答案应该 ≤ 2）
4. 上一个结论有**几条独立证据**？
5. 上轮**证伪了什么**？（没有证伪也要写「无」）

### 每次验收，看这三样

1. 判据里的数字**改前 / 改后**各是多少；
2. 默认基线四个数有没有变化，变化能否解释；
3. 至少一条已有闭环**重跑通过**。

### 出现这些话，要追问

| 听到 | 追问 |
|---|---|
| 「应该是 XX 的问题」 | 「什么结果会证明不是？」 |
| 「日志很干净」 | 「画面呢？端到端判据呢？」 |
| 「看起来正常」 | 「换成数字怎么说？」 |
| 「探针没输出，所以没调用」 | 「探针限流了吗？第二个独立证据是什么？」 |
| 「顺手也改了 B」 | 「单变量 A/B 还成立吗？B 的回归跑了吗？」 |
| 「这个之前修过了」 | 「D 号是多少？清零索引里怎么写的？」 |

### 你要保护的三种文化

- **「我错了」可以公开写**：D199 那次六轮误判之所以能一次纠偏，
  是因为每一步都留在台账里。若当初悄悄改掉，后面还会继续在错快照上堆假设。
- **不知道就标注不知道**：`switch-desc.txt` 里「不知道就留空，那是诚实的债」
  比编一句似是而非的说明有价值得多。
- **红灯必须值得处理**：门禁长期失败等于没有门禁；宁可降级为警告，也不要留一个没人看的红灯。

## 8. 一页检查清单（例会可直接照念）

```
□ 现在卡在哪一层？能否用一句话说清？
□ 卡点的判据是可执行的命令 / 数字，还是形容词？
□ 上一轮结论的证据 ≥ 2 条且来源不同？
□ 本轮假设有没有写进假设台账？被否掉的记了吗？
□ A/B 是不是只改了一个变量？主指标变了吗？
□ 对照是否同一序列、同一超时、同一截图点、全默认配置？
□ 测量工具（探针 / 计数脚本）自己验过吗？
□ 默认基线四个数 + 一条已有闭环重跑了吗？
□ 临时探针删干净了吗？新开关登记了吗？门禁过了吗？
□ 改动影响面清单填了吗？失败怎么回退？
□ 状态文档更新了吗？方法论 / 归档各归位了吗？
□ 这轮预算用完了吗？该停下来重新验证工具了吗？
```

> 项目健康的标准不是「没有 bug」，而是**这十二个问题随时都能回答**。
> 如果第 1 条答不上来，说明还在凭感觉改代码。
